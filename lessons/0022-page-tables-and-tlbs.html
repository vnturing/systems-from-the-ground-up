Page tables and TLBs

Distinguish translation-cache misses from faults and data-cache misses.

Builds on Lesson 21: Translate a virtual address. Follow the course order on a first pass.

Caching the map is different from caching the data

A translation lookaside buffer caches address translations. A data cache stores data blocks. The same load can hit in one and miss in the other. Conflating those events leads to weak performance explanations.

A TLB miss means the translation is absent from that translation cache. If page-table entries describe a valid accessible mapping, translation can be recovered, often through a hardware walk on our main targets. A page fault means the access requires operating-system handling because a translation or permission condition was not satisfied. A data-cache miss means the requested data block is absent at that cache level. OSTEP's TLB chapter develops this distinction. OSTEP — Faster Translations (TLBs)

Derive why one flat table is expensive

Assume 48-bit virtual addresses, 4 KiB pages, and eight-byte leaf entries. There are 2^(48-12) = 2^36 virtual pages. A fully populated flat table would need 2^36*8 = 2^39 bytes, or 512 GiB, for one address space. This is an illustrative address-space calculation, not a claim that every x86 processor uses exactly 48 virtual bits today.

Multi-level page tables allocate lower-level tables only for populated ranges. With 4 KiB table pages and eight-byte entries, each table holds 512 entries, consuming nine index bits per level. Four such levels plus a 12-bit offset account for 48 bits in a simplified common x86-64 layout. Other configurations use different depths and page sizes. Intel — architecture and optimization manuals

Sparse mappings save memory, walks add work

If a program touches only a few ranges, most lower-level tables need not exist. But a miss in translation caches can require several dependent memory references to walk the structure. Caches of page-table data and intermediate translations reduce this cost. A simple “every load always requires four extra DRAM accesses” model is therefore too pessimistic.

TLB reach is roughly the number of entries times the page size for a particular translation-cache structure. A 64-entry toy TLB with 4 KiB pages covers 256 KiB if each entry maps a distinct ordinary page. Larger pages can increase reach, but have allocation, fragmentation, permission-granularity, and OS-policy tradeoffs.

Why strides can stress two hierarchies

A loop reading one byte from each of thousands of pages uses little useful data per page and may exceed TLB reach. It can also create data-cache misses. To distinguish these effects experimentally, vary page count, within-page reuse, and data footprint, then choose appropriate events if available.

Context switches require translations to remain associated with the correct address space. Address-space tags can preserve useful entries across some switches; changing page tables may require invalidation or coordination across cores. Consult the target and OS rather than claiming that every context switch flushes every TLB entry. Arpaci-Dusseau & Arpaci-Dusseau — Paging: Introduction

Worked feedback

There are 2^20 pages and entries, requiring 2^22 bytes, or 4 MiB. No: the mapping and data may be resident while only the cached translation is missing. If you answered one million bytes, you counted entries but forgot the entry size.
