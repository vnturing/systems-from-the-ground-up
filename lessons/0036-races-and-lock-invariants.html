Races and lock invariants

Explain a lost update and choose the invariant a lock must protect.

Builds on Lesson 35: Readiness and backpressure. Follow the course order on a first pass.

An increment is not a protocol

In a simple interleaving model, counter++ contains a read, an addition, and a write. Two workers can both read zero, compute one, and store one, losing an update. The browser scheduler makes that finite sequence visible.

For an actual C program, conflicting non-atomic accesses without the required synchronization form a data race and invalidate the program's behavior under the language model. It is insufficient to say it merely “sometimes returns one.” Compiler transformations make the real consequence broader than our pedagogical schedule. The draft's execution and atomic rules establish this boundary. WG14 N1570 — public C11 committee draft

Protect an invariant, not a token line

Suppose a queue has a buffer, head, tail, and count. The invariant relates them: count remains in range, head identifies the next item, tail identifies insertion position, and each queued item appears exactly once. Locking only count++ while modifying the other fields without protection does not preserve that structure.

Choose one mutex that protects the whole relationship. Every path that reads or changes the protected state must follow the same discipline, including error and shutdown paths. A comment such as “mutex protects head/tail/count and buffer slot ownership” is more useful than “thread-safe.”

Locking has its own contract

Acquire before the protected access and release on every relevant path. A mutex is not generally recursively acquirable unless configured that way; self-deadlock is possible. POSIX thread operations return error codes through their specified return values, often directly rather than through errno.

Locks coordinate access and visibility when used according to the platform/language contracts. They do not extend a freed object's lifetime automatically. The lock object itself must remain alive until nobody can use it.

Challenge the design with tools

ThreadSanitizer can report exercised data races on supported platforms. Build separately from AddressSanitizer and keep workload coverage and tool limitations visible. A clean run is evidence about that execution, not a proof of race freedom. Clang — ThreadSanitizer

OSTEP's lock treatment explores implementation tradeoffs such as spinning versus blocking and fairness. Application code should ordinarily use established primitives rather than writing a lock from a guessed assembly instruction. OSTEP — Locks

Mutual exclusion is one correctness property

A program can be race-free yet deadlock, violate ordering requirements, or process an item twice. Correctness needs both safety (“bad things do not happen”) and progress obligations (“required work can eventually proceed under stated assumptions”). A mutex prevents simultaneous critical sections; it does not decide who owns a work item after the critical section ends.

Move long I/O or callbacks outside a lock when the invariant and lifetime allow it. Holding a global mutex across a slow network write can serialize otherwise independent work. Copying a pointer out before unlocking is only safe if the target remains alive through its use.

Retrieve before looking

A queue updates head and count under a lock but reads count without locking to decide whether to sleep. Why is this incomplete? Name both a language-level and a protocol-level concern.

Worked feedback

The unsynchronized ordinary read can race with updates. Even replacing count with an atomic does not by itself coordinate the check with entering a wait, so a notification can be lost. Correct waiting must protect the predicate and atomically release the mutex while waiting, which the next lesson develops.
