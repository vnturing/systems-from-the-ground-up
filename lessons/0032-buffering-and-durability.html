Buffering and durability

Explain which layer acknowledged a write and what remains unproven.

Builds on Lesson 31: Robust I/O loops. Follow the course order on a first pass.
In this lesson

Success has a layer

A call to fprintf may update a user-space buffer without issuing a kernel write immediately. fflush pushes buffered output through the stream's underlying mechanism. A successful write means the kernel accepted the reported bytes under that interface; it does not universally prove persistence after power loss. Synchronization interfaces add a different guarantee. Linux man-pages — write(2) Linux man-pages — fsync(2)

Name the layer in every statement: application record created, stdio buffer accepted, kernel accepted, file state synchronized, or directory update synchronized. “The data was saved” is too ambiguous for a failure investigation.

Buffering changes observations

A terminal may show line-buffered output promptly, while a redirected stream may be fully buffered. That can make the same program appear to hang or reorder messages relative to an unbuffered channel. An explicit flush is appropriate when the interface requires immediate visibility; flushing after every character can create unnecessary syscall overhead.

Avoid casually mixing stdio operations with raw descriptor operations on the same underlying file. They can have separate buffering state but share offsets through an open-file description. Coordinating them requires the relevant stream rules; separate handles are not independent snapshots. Linux man-pages — dup(2)

Atomic replacement is a protocol

A common local-file update pattern is to create a temporary file in the destination filesystem, write a complete new version, synchronize required file state, rename it into place, then synchronize the containing directory as required for the intended durability contract. Check every operation and define recovery behavior.

A rename can provide atomic namespace replacement under the relevant filesystem rules; atomic visibility is distinct from crash persistence. File and directory synchronization behavior depends on the OS/filesystem/storage stack. The Linux fsync manual explicitly discusses directory entries. This lesson is a reasoning guide, not a universal database recovery proof. Linux man-pages — fsync(2)

Failure can arrive late

Storage errors may be reported on a later write, synchronization, or close rather than at the exact point the application first produced the data. Ignoring cleanup and synchronization errors can therefore lose the only signal that a supposedly successful operation failed.

For a copy utility, clearly state whether success means “all bytes delivered to the output descriptor” or “durably stored as a named file.” Lab 06 tests byte-transfer correctness and error reporting; it does not claim crash durability.

Append and transactions are separate

Opening in append mode can coordinate where each kernel write begins, but a logical record split across several writes may interleave with other writers. A single write's atomicity depends on object type and applicable limits. Pipes have their own atomic-write bound; regular-file behavior is a different contract.

Even a durable sequence of independent writes is not automatically an atomic multi-record transaction. A recovery protocol must determine which partial states are valid and how to detect or repair them. Checksums, commit records, and journaling belong to that larger design.

Retrieve before looking

After a successful write and before fsync, the machine loses power. What can the application conclude from its earlier return value? What additional namespace issue remains if a new file was created?

Worked feedback

The return value established that the reported bytes were accepted by the write interface, not that power-loss persistence was complete. A newly created or renamed pathname involves directory metadata that may need its own synchronization for the intended guarantee. Exact recovery depends on the platform and filesystem; do not infer it from a normal-exit test.

Transfer

Write two success contracts for a file-producing command: one for an ephemeral pipeline and one for a durable configuration replacement. Identify which extra operations and failure checks the second contract requires.
