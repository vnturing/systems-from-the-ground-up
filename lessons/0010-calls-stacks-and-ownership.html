Calls, stacks, and register ownership

Explain what must survive a function call and who preserves it.

Builds on Lesson 09: Recover control flow. Follow the course order on a first pass.

A call is an agreement

A function boundary crosses separately compiled code. The ABI specifies where arguments and results live, which registers the callee must preserve, and how the stack is aligned. A function may have correct arithmetic and still break its caller by violating that agreement.

Under System V AMD64, %rbx, %rbp, and %r12–%r15 are preserved by the callee. Many other ordinary registers are caller-saved: a caller that needs their values after a call must arrange preservation itself. %rsp must also be restored appropriately. The exact rules include more detail for vector registers and complex signatures. x86-64 psABI — official project

Trace a nested call

Suppose outer(x) needs x after calling inner(x). Keeping x only in %rdi is insufficient because inner may overwrite it. The compiler can spill x to the stack, copy it into a callee-saved register after preserving that register's original value, or recompute it if possible.

A conventional x86 call stores a return address on the stack and transfers control. ret obtains the saved return address and continues there. The stack is also used for spills, some arguments, saved registers, and addressable locals. It is not merely a pile of C variables.

At ordinary System V AMD64 function entry, %rsp + 8 has the required 16-byte alignment because the call pushed eight bytes. A call-site convention and an entry convention are easy to confuse. The ABI also defines a red zone for particular uses; signal and kernel contexts have different constraints. Do not build handwritten assembly from a simplified drawing alone.

Stack frames are a debugging aid

At low optimization, a frame pointer often makes the call chain and locals easy to inspect. Optimized code can omit it, inline functions, or perform tail calls. Unwinding may use metadata instead. A missing source frame in a debugger does not automatically mean the stack is corrupt.

Use backtrace, frame, info registers, and disassembly to align three views: the source call, the instruction pointer, and the stack's saved state. GDB documents both source and machine-level examination. GDB — current manual

AArch64 changes the return mechanism

AArch64 commonly places the return address in link register x30 rather than pushing it automatically. A function making another call must preserve its own return address somewhere suitable, often its stack frame. The stack pointer has alignment requirements, and the AAPCS64 defines a different preserved-register set. Arm — AAPCS64

This comparison reveals the stable idea: a return path and caller state must survive nested calls. The particular register names and automatic stack action are ISA/ABI details. It also explains why copying an x86 stack diagram directly onto Apple Silicon is misleading.

Retrieve before looking

A caller stores a needed temporary in a caller-saved register, invokes an unknown ABI-conforming function, and uses the temporary afterward. Who was responsible for preserving it? Can a successful run prove the code is safe for every callee?

Worked feedback

The caller was responsible. The particular callee in one run may happen to leave the register unchanged, but another valid implementation may clobber it. Correctness depends on the ABI contract, not a lucky observation. If the callee instead damages a callee-saved register without restoration, the callee is at fault.
