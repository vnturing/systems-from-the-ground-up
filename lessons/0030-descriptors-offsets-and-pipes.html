Descriptors, offsets, and pipes

Draw descriptor ownership and explain shared offsets and pipe EOF.

Builds on Lesson 29: Signals without races. Follow the course order on a first pass.

An integer is a handle, not the file

A file descriptor is a small integer in a process's descriptor table. The entry refers to an open-file description that can hold offset and status state. Separate descriptor entries can refer to the same description; separate opens of one pathname can refer to different descriptions for the same underlying file.

After dup, both descriptors share the open-file description's offset. Reading three bytes through one can make the next read through the other begin at byte three. They do not become independent cursors merely because their integer handles differ. The dup interface documents this sharing. Linux man-pages — dup(2)

Fork copies handles, not independent file state

Parent and child inherit descriptor entries referring to corresponding open-file descriptions. Their private C variables diverge, but shared file offsets and underlying objects can still coordinate behavior. This is an important counterexample to “fork makes everything separate.” Linux man-pages — fork(2)

Closing one descriptor removes that process's reference. It does not necessarily close every other reference to the open-file description, including references in another process. dup2 can atomically replace a target descriptor with a reference to a chosen description, making it useful for redirecting standard input or output.

Pipes are lifetime protocols

A pipe has a read end and a write end. A reader gets bytes while bytes are available; it observes EOF after the buffer is drained and all writer references are closed. If the parent accidentally retains a write endpoint, the child reader can wait forever even when the intended producer has exited.

Likewise, writing when no readers remain can generate SIGPIPE or report EPIPE under the configured signal behavior. An error-handling strategy must account for the process being signaled before ordinary code sees the return value.

Draw a pipeline before coding

For a producer connected to a child utility, label endpoints r and w. After fork, both processes initially have both endpoints. The producer closes r; the child maps r to standard input, closes the original r when appropriate, and closes w. The producer writes, closes w, and waits. Exact handling must account for descriptors already equal to the intended target in more general code.

Lab 05 uses a controlled invocation to make the ownership visible. Its completion check detects the resulting transformed bytes, not a particular interleaving of diagnostic output.

“Everything is a file” has limits

Descriptors provide a common handle abstraction, but regular files, pipes, terminals, and sockets have different seek, readiness, buffering, and EOF behavior. read asks for up to a count; short results and EOF depend on the object. A pipe is a stream, not an array with an automatically known final size. Linux man-pages — read(2)

A descriptor number may be reused after close. Keeping an old integer in a struct and using it later can target an unrelated newly opened object. This is a handle-lifetime bug analogous to a dangling pointer.

Retrieve before looking

Two processes share a pipe. The producer closes its writer, but the consumer still holds its inherited writer open while reading. Why can EOF fail to arrive? Which exact reference must be removed?

Worked feedback

At least one write reference remains: the consumer's unintended inherited writer. EOF depends on all writers closing, not on one designated producer finishing. The consumer must close its writer endpoint. A wait in the producer does not close the consumer's reference.
