Atomics and publication

Distinguish an atomic counter from a safe data-publication protocol.

Builds on Lesson 37: Condition variables and queues. Follow the course order on a first pass.

Atomicity and ordering answer different questions

An atomic increment prevents conflicting updates to that atomic object from losing each other's changes under the atomic contract. Memory ordering determines relationships with other operations. Relaxed atomics can be appropriate for an independent statistic that does not publish other data; they do not automatically make a separate ordinary payload safe to read.

Use <stdatomic.h> and the C atomics interfaces. Whether an atomic type is lock-free depends on the target and type. Atomic does not mean every operation is one instruction or that a whole algorithm is nonblocking. The public draft describes the language model in §§5.1.2.4 and 7.17. WG14 N1570 — public C11 committee draft

State a publication protocol precisely

Assume one writer, one reader, a payload alive for the entire interaction, and one publication:

c
/* initially: atomic_bool ready = false; int payload; */
/* writer */
payload = 42;
atomic_store_explicit(&ready, true, memory_order_release);
/* reader */
if (atomic_load_explicit(&ready, memory_order_acquire)) {
    /* safe to read payload for this one-publication protocol */
}

The acquire that reads the published true synchronizes with the release. The writer's earlier payload write is then ordered before the reader's subsequent read. If the acquire sees false, it has not received that publication and must not read the uninitialized payload under this protocol.

Do not quietly generalize the example

Resetting the flag and reusing the payload repeatedly introduces new lifetime and ordering questions. A second writer can invalidate the single-writer argument. Freeing the payload while a reader still holds a pointer is a separate reclamation problem. Release/acquire is not a generic permission to read all shared memory forever.

For complicated ownership or multi-field invariants, a mutex is often clearer. Use the narrowest protocol you can prove and test. Handwritten lock-free structures require an explicit progress argument and memory reclamation design in addition to atomic instructions.

Hardware explanations come after language correctness

Different CPUs implement ordering constraints with different instructions or barriers. A store/load sequence that appears reliable on x86 can fail as a portable source protocol because the compiler and language contract remain relevant. volatile does not replace atomic synchronization.

The kernel barrier guide is useful advanced reading about ordering mechanisms, but its model and primitives are not the user-space C standard. Keep those domains separate. Linux kernel — memory barriers

Compare-exchange does not solve reclamation

A compare-exchange checks and updates one atomic object under its specified semantics. A pointer value changing A→B→A can make a simple equality check miss intervening history: the ABA problem. If A's storage was freed and reused, dereferencing the “same” address adds an object-lifetime hazard.

Hazard pointers, epochs, and other reclamation schemes address different aspects of this problem and require substantial protocols. Do not turn a stack using compare-exchange into a claim of safe lock-free memory management without that additional work. TSan can expose exercised races, but cannot prove an arbitrary lock-free algorithm correct. Clang — ThreadSanitizer

Retrieve before looking

Why is a relaxed atomic ready flag insufficient to publish an ordinary payload? Under the single-publication assumptions, which two operations need release and acquire semantics?

Worked feedback

Relaxed access coordinates the flag itself without establishing the required synchronization for the payload. The writer's store to the flag uses release; the reader's load that observes it uses acquire. The payload must remain alive and no conflicting later write may violate the protocol. Repeating only the keywords without those assumptions is incomplete.

Transfer

Choose between a mutex and an atomic for three tasks: count completed independent jobs, publish an immutable configuration once, and mutate a queue with head/tail/count. Explain the invariant, not merely the expected instruction cost.

Retrieval check

A writer stores data, then release-stores ready=true. A reader acquire-loads that true from the store. What relation is established?

Go to the source

The first source is the recommended primary reading. Read for the question taught here; these links are extensions, not prerequisites to understanding the page.

  • WG14 N1570 — public C11 committee draft

    Language contracts: §§6.2 (types, lifetime, representation), 6.3 (conversion), 6.5 (expressions), 7.22.3 (allocation), 7.17 (atomics). The labs compile as C17 and use the shared subset; this older draft is not the final C17 standard.

  • Linux kernel — memory barriers

    Advanced comparison for compiler/CPU ordering. Kernel primitives and the Linux memory model do not replace C's user-space atomics contract.

  • Clang — ThreadSanitizer

    Find exercised data races. Build separately from AddressSanitizer; platform support varies.
