Locality and blocking

Spatial and temporal reuse are distinct

Spatial locality means nearby bytes are used together. Temporal locality means recently used data is used again soon. A sequential pass can have strong spatial locality while touching each element only once. A tiny hot lookup table can have strong temporal locality even when indices look irregular.

A cache line pays for a group of nearby bytes. If an eight-byte element sits in a 64-byte line, a contiguous traversal can use eight elements from that line. A stride of one large row between loads may use only one element before moving elsewhere. This is a concrete reason for different traffic, not a slogan that “arrays are fast.”

Reuse distance connects code to capacity

Imagine iterating columns outside and rows inside on a 2048-by-2048 matrix of four-byte elements. Consecutive inner-loop accesses are 8192 bytes apart. Returning to a nearby element in the same row may happen only after touching thousands of other lines. Whether that earlier line survives depends on the cache's sets, capacity, associativity, and other traffic.

Reversing loop order makes neighboring inner-loop accesses contiguous. It may improve useful bytes per fetched line even if both versions perform the same arithmetic. Compilers may transform loops, so inspect generated behavior before attributing every difference to the source order. GCC — optimization options

Blocking bounds the live footprint

For a matrix operation that reuses tiles from three arrays, a first footprint estimate for square tile side T and element size d is 3*T*T*d. With T = 32 and d = 8, that is 24,576 bytes. This suggests a candidate tile size, not a guarantee of fit: associativity conflicts, other data, write policies, and alignment matter.

Choose several nearby tile sizes and test correctness and performance. Include sizes not divisible by the tile side. Edge tiles require clipped bounds; optimizing only square multiples is not a complete implementation.

A useful laboratory result is allowed to be boring

Lab 03 checks that two traversal orders produce the same integer checksum, then records repeated timings. If your matrix fits in cache or the compiler interchanges loops, the difference may be small. Report that outcome honestly. Increase the working set within your machine's limits or inspect the compiler's loop transformations before inventing a cache story. Brendan Gregg — perf examples

Data layout is another loop transformation

An array of records loads unused fields if the loop needs only one member. Separate arrays can make the needed field contiguous, improving line utilization and vectorization. But code that uses all fields together may favor records, and reorganizing data has allocation and interface costs.

Drepper's investigation motivates thinking about traffic and locality rather than instruction count alone. Treat its examples as mechanisms to investigate on your hardware, not as universal rankings. A complete argument names the hot fields, access order, element size, cache boundary, and measured consequence. Ulrich Drepper — What Every Programmer Should Know About Memory

Retrieve before looking

A row contains 1024 eight-byte elements. What is the byte stride when traversing a fixed column down successive rows? How many elements fit in an assumed 64-byte line during a contiguous row traversal?

Worked feedback

The stride is 1024*8 = 8192 bytes. Eight elements fit in a 64-byte line, subject to alignment at the beginning/end. The line size is an explicit assumption; inspect your target if it matters. Knowing those numbers does not yet prove the miss rate, because retention and mapping still matter.

Transfer

Extend Lab 03 with blocked traversal and a non-multiple matrix dimension. Keep the exact checksum oracle. Before running it, predict which tile sizes are too small to reduce overhead and which may exceed a chosen cache footprint.
