Deadlock and scaling

Draw a wait cycle and separate correctness from throughput.

Builds on Lesson 38: Atomics and publication. Follow the course order on a first pass.

Progress needs a separate argument

Race freedom does not guarantee progress. Two threads can legally hold different locks while each waits for the other's lock. Draw a wait-for graph: thread A points to a resource held by B, and B points back through another resource. A cycle identifies a possible deadlock under this model.

Use a global lock order when operations require multiple locks. If every operation acquires lower-ranked before higher-ranked resources, the specific circular-wait pattern is prevented. Include callbacks and error paths in the rule; a hidden reverse acquisition is still a reverse acquisition. OSTEP explores locking mechanisms and their progress tradeoffs. OSTEP — Locks

Avoid waiting for work that needs your lock

Holding a queue mutex while joining a worker can deadlock if the worker needs that mutex to finish. Holding a global mutex while making a blocking network write can stall unrelated tasks behind a slow peer. Even without a strict cycle, long critical sections can cause severe queueing.

Restructuring requires ownership reasoning: extract or reserve the needed data under the lock, release it, perform slow work, then commit under the appropriate validation if necessary. Copying an unprotected pointer and hoping its object survives is not a safe shortcut.

More workers can create less useful work

Throughput initially rises when independent work uses spare cores. It can flatten or decline under contention, bandwidth saturation, scheduling overhead, false sharing, or an inherently serial stage. Latency can worsen before maximum throughput is reached because requests wait in queues.

Measure completed useful jobs per unit time, response-time distributions, queue depth, resource use, and correctness. A CPU graph at 100% is not evidence that every cycle serves useful work. Spinning can saturate CPU while progress remains poor.

Choose a discriminating observation

If the global lock dominates, shorten the critical section or shard state and measure wait/hold behavior. If memory bandwidth dominates, extra workers may add traffic without increasing throughput. If output backpressure dominates, inspect pending bytes and peer consumption. Gregg's USE method turns these into resource questions; profiling examples provide concrete collection techniques on supported Linux environments. Fairness, starvation, and livelock

A design can avoid deadlock yet starve a participant indefinitely under its scheduling assumptions. Livelock means participants keep changing state without completing useful work. Random retries can reduce collisions statistically, but do not automatically establish a strong progress guarantee.

Specify the guarantee you actually need: eventual shutdown, bounded queue size, no permanently stranded items, or a particular fairness property. The platform's mutex and condition-variable contracts may not promise the exact FIFO wakeup order you imagined. Design correctness without relying on accidental scheduler behavior.

Retrieve before looking

A controller holds the queue mutex and calls join on consumers. The consumers wake on close but must reacquire that mutex to observe the closed state. Explain the wait cycle and a corrected shutdown order.

Worked feedback

The controller waits for consumers to terminate while retaining the mutex they need to progress. Set closed and broadcast under the mutex, release the mutex, then join workers, and only afterward destroy synchronization objects. This sequence lets awakened workers observe the predicate and exit. Every resource must remain alive until its last use.

Transfer

Write a scaling investigation for Lab 08 with one, two, four, and more workers where available. Distinguish a scheduling-dependent result from a correctness assertion. Use the same workload and report the queue's capacity as part of the experiment.

Retrieval check

Thread A holds L1 and waits for L2; thread B holds L2 and waits for L1. Which design change prevents this lock-order cycle?
