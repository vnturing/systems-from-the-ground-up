Fork, exec, and wait

Account for parent and child paths, image replacement, and reaping.

One call, two continuations

After successful fork, the parent receives the child's positive PID and the child receives zero. A negative return indicates failure in the parent; no child was created. Both successful paths continue after the call. Their ordinary private variables begin with corresponding values but subsequently belong to separate address spaces. Linux man-pages — fork(2)

Draw the control-flow tree before predicting output. After two unconditional successful forks there can be four processes, because both existing processes execute the second call. Conditional branches can change the tree; a memorized power-of-two rule is not a substitute for tracing them.

Replace an image deliberately

A child often rearranges descriptors and calls an exec-family function. Success replaces its program image and does not return. Failure returns to the old code and requires an error path. Arguments are an array of pointers terminated by a null pointer; the strings have their own terminators. Process arguments and shell command parsing are not the same thing. Linux man-pages — execve(2)

After a failed exec in a forked child, _exit is usually the appropriate termination primitive for the simple pattern in this course. Calling normal exit can run inherited buffered-output flushing or cleanup in an unintended context. Before fork, buffered stdio data is user-space state that can be copied into both processes.

Reap and interpret status

A terminated child leaves status for its parent. waitpid collects it; retry appropriately if interrupted. The returned status is encoded. Check WIFEXITED before WEXITSTATUS; check WIFSIGNALED before WTERMSIG. Do not treat the raw integer as the child's return code. Linux man-pages — waitpid(2)

A zombie is a terminated child whose status has not been reaped, not a still-running worker consuming ordinary execution time. A parent needs a deliberate policy for every child: wait now, reap later, or hand responsibility to a well-defined supervisor.

Inheritance has multiple layers

File descriptors survive fork and refer to shared open-file descriptions, so file offsets can be shared even while user-space memory is private. Descriptor close-on-exec flags affect what survives a successful exec. The parent and child each need to close their own unused pipe endpoints. A pipe reader cannot observe EOF while any writer endpoint remains open.

Forking a multithreaded process is harder

After fork in a multithreaded process, only the calling thread remains in the child, while copied library state may reflect locks held by vanished threads. Between fork and exec, POSIX imposes strict constraints on operations the child can safely perform. The lab uses a simple single-threaded parent and a controlled child path; do not generalize arbitrary C library activity there to a threaded server.

Creation, replacement, and reaping solve separate problems. A compact shell pipeline can involve all three plus descriptor ownership. Use a process/descriptor diagram to keep the obligations visible.

Retrieve before looking

A parent forks, the child successfully execs a utility, and the parent waits. How many processes were created by fork and by exec? Why might output without a newline printed before fork appear twice when redirected?

Worked feedback

Fork creates one child; exec creates no additional process. Redirected stdio may leave the pre-fork text buffered in user memory. Both processes inherit that buffer, and normal exit can flush both copies. Flush deliberately before fork or avoid that output pattern; use the child termination protocol appropriate to the design.
