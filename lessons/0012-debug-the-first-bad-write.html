Debug the first bad write

Distinguish the observed crash from the earlier operation that caused it.

Builds on Lesson 11: Recover data layout. Follow the course order on a first pass.

The faulting line is a witness

A crash tells you where execution encountered a problem it could not continue through. It does not necessarily identify the original mistake. A buffer overrun can damage a neighboring pointer; much later, an innocent-looking dereference faults.

Use a small input that reproduces the symptom. Record the exact compiler flags, executable, input, and command. Rebuild with debug information and a manageable optimization level, then inspect the failing state. Keep the original optimized reproducer too: timing, layout, and undefined behavior can change with instrumentation.

Ask the debugger a question

For Linux with GDB, a useful sequence is:

text
gdb ./program
break main
run
backtrace
frame 0
info locals
info registers
x/16bx address

Replace address with an actual object address obtained from the current frame. x/16bx examines sixteen bytes in hex. next steps over source calls; step enters them; stepi advances an instruction. A watchpoint on a live object can stop when its value changes, helping identify the first unexpected writer. Hardware resources constrain watchpoint sizes and counts. GDB — current manual

On macOS use LLDB's breakpoint set, run, bt, frame variable, register read, and memory read; the official command map translates workflows. Attaching or launching may require local debugger permissions that a hosted environment lacks. LLVM — GDB to LLDB command map

Instrument a hypothesis

Build the Lab 02 memory example with AddressSanitizer. The report distinguishes an access site, the accessed address's relationship to an allocation, and often allocation or release stacks. Read all three. “Heap-use-after-free” is an explanation of a violated lifetime, not just an intimidating label. Clang — AddressSanitizer

Repair the cause in source and rerun both the reproducer and boundary inputs. A successful run with the old input is necessary evidence, but not the whole repair: explain which invariant now prevents the class of violation. Examples include an explicit capacity check, a corrected ownership transfer, or removal of an invalid returned pointer.

Readable memory is not valid C storage

A debugger can show bytes at a dead object's former address. The operating system may still map the page, and the bytes may look exactly as expected. Neither fact restores object lifetime. Similarly, writing outside a small array can stay inside a mapped page and avoid an immediate hardware fault.

Sanitizers add a layer that catches some language-level violations invisible to page protection. They have runtime and platform limitations, and only inspect exercised paths. Combine a concrete report with a reasoned contract; do not equate silence with proof.

Retrieve before looking

Your program faults while reading node->next. List three earlier causes that could produce this symptom and one observation that would distinguish each.

Worked feedback

The node may have been freed: inspect release history or an ASan use-after-free report. The pointer may have been overwritten: a watchpoint or nearby bounds report can identify a writer. The object may never have been initialized: trace construction and assignments, possibly using an appropriate uninitialized-memory tool. A null value is another possibility, but it does not explain why it became null. The exercise is to move from symptom to testable history.

Transfer

Produce a short investigation note for Lab 02: symptom, violated invariant, earliest demonstrated bad operation, repair, and evidence against a competing hypothesis. This note is more valuable than a screenshot of a clean exit.
