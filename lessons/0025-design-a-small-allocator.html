An arena exposes the core obligations

An arena reserves backing storage and advances a cursor for allocations. It can release everything at once by resetting the cursor. It is useful when many objects share a lifetime, such as one parsed request. It cannot individually free arbitrary objects unless you add more machinery.

Before returning an address, align the cursor and check remaining capacity. For power-of-two alignment A, padding is (A - used%A)%A. Check padding <= capacity-used and then size <= capacity-used-padding before advancing. These subtraction-based checks avoid overflowing a speculative used+padding+size.

The arena's base must itself satisfy the required alignment. Aligning an offset cannot repair a misaligned base. Lab 04 uses a max_align_t-aligned buffer and supports ordinary alignments up to that limit; it is not an over-aligned general-purpose replacement for malloc.

Free lists buy flexibility with metadata

A reusable allocator can track blocks with sizes, allocation state, and links between free blocks. To serve a request, round for alignment, add overhead safely, choose a free region, and split only if the remainder can represent a valid free block. On release, coalesce adjacent free blocks where the representation permits.

A first-fit policy chooses the first sufficiently large block. Best-fit seeks a close size match but may leave tiny unusable fragments and add search cost. Segregated lists group sizes for faster selection. Policy is a workload tradeoff, not a universal ranking. OSTEP develops these design choices and fragmentation distinctions. OSTEP — Free-Space Management

State invariants before writing code

For an arena: cursor never exceeds capacity, returned ranges do not overlap while live, each return meets alignment, and failure leaves the arena unchanged. After reset, previous arena objects must no longer be used.

For a free-list allocator: every block's size is valid and aligned, blocks partition the managed region, allocated blocks do not overlap, free-list links refer only to free blocks, and each free block appears exactly once. If immediate coalescing is promised, no adjacent free blocks remain separate. These invariants guide tests more effectively than “allocate ten things and see.”

Measure fragmentation honestly

Internal fragmentation is unused space inside an allocated block, such as rounding slack. External fragmentation is free space divided into regions that cannot satisfy a request, despite sufficient total free bytes. Metadata overhead is another cost. Keep them separate when comparing allocators.

Space and throughput can conflict

An allocator can reduce search time by reserving more classes or keeping per-thread caches, increasing memory retained outside the application's current live set. Releasing an object does not guarantee an immediate drop in process RSS. The system allocator may keep storage for reuse rather than return whole pages to the OS. Linux man-pages — malloc(3)

A reset-based arena avoids many free-list issues but moves responsibility into lifetime grouping. If one long-lived object keeps a request arena alive, the entire arena can remain retained. The right interface is the one whose lifetime matches the workload, not the one with the shortest allocator implementation.

Retrieve before looking

An arena base is eight-byte aligned, cursor 13, capacity 40, and request size 16 with alignment eight. Calculate padding, returned offset, and new cursor. Would a following 16-byte request at the same alignment fit?

Worked feedback

Padding is three; return offset is 16 and new cursor 32. A following aligned 16-byte request would end at 48, exceeding capacity, so it must fail without changing the cursor. The failure check should compare against remaining space before computing an overflowing end offset in a real large-size case. Alignment contracts follow the language's object requirements.
