Robust I/O loops

Handle partial progress without losing or duplicating bytes.

Builds on Lesson 30: Descriptors, offsets, and pipes. Follow the course order on a first pass.
In this lesson

A count is progress

A positive read or write result is the number of bytes transferred, not a Boolean success flag. A result smaller than requested can be normal. read returning zero indicates EOF for the stream situations used here. A negative result signals an error; inspect errno only when the interface indicates failure. Linux man-pages — read(2) Linux man-pages — write(2)

For an exact-length blocking receive, track done. On a positive result, increase it. On zero, decide whether EOF before completion is a valid protocol ending or truncation. On interruption with EINTR, retry according to the operation's contract. Other errors terminate or transfer responsibility to the caller.

Prove the loop invariant

For a complete write, the invariant is “bytes [0, done) have been sent exactly once; bytes [done, length) remain.” Each successful call begins at buffer + done and requests length - done. This prevents both duplication and gaps.

If a positive-length write reports no progress, do not spin forever. Treat it as a defined error condition in this helper. For nonblocking descriptors, EAGAIN means wait for readiness and resume later; repeatedly calling in a busy loop defeats the design. The lab's helper explicitly assumes blocking I/O and reports other errors to its caller.

Bound before subtraction and conversion

Store capacities in size_t, but syscall results in ssize_t. Test for negative before converting to an unsigned count. A negative ssize_t converted to size_t becomes a huge value, which can corrupt an offset calculation.

Keep every request inside the valid buffer and within platform interface limits. length - done is safe only if done <= length is an invariant. A helper's signature does not excuse a caller from supplying live storage of the promised size.

Test failure paths deliberately

Ordinary regular-file writes often complete fully, so a successful copy of one small file does not exercise the loop. Lab 06 injects a deterministic sequence of short counts and an interrupt into the actual compiled helper by substituting its write dependency. It separately tests the real compiled copy program with binary data and a closed-pipe error path. Injected-boundary tests and system tests answer different questions.

Retry is an operation-specific policy

Do not blindly retry every failed system call. Some calls can have side effects before reporting a failure, and some close/interruption semantics differ by OS. The rule here applies to the documented byte-transfer loop, with explicit progress accounting.

Signals can interrupt blocking operations, while restart settings may cause some operations to resume automatically. Design around the interface's permitted results instead of assuming the handler configuration guarantees a full transfer. Linux man-pages — signal(7)

Retrieve before looking

A ten-byte send receives return counts 3, -1/EINTR, 2, and 5. List the buffer offset and requested remaining length before each call. Is the error count ever added to progress?

Worked feedback

Offsets/lengths are (0,10), (3,7), (3,7), and (5,5). The interrupt adds no progress in this sequence; the next attempt resumes at three. Positive results total ten. Adding the signed error result or restarting at zero breaks the invariant.

Transfer

Review Lab 06's copy loop and Lab 07's socket helper with the same invariant. Then design an API that distinguishes clean EOF before a new frame from EOF in the middle of a frame; the difference becomes a protocol correctness requirement.

Retrieval check

write returns 7 after you requested 20 bytes. What is the next remaining range?
