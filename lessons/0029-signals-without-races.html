Signals without races

Design a minimal handler and explain the lost-wakeup race.

Builds on Lesson 28: Fork, exec, and wait. Follow the course order on a first pass.

Delivery is not an ordinary callback

An asynchronous signal can interrupt code between operations that a library assumes are coordinated. A handler that calls printf or malloc can reenter internal state that was already mid-update. The list of async-signal-safe functions is a real contract, not a style preference. Linux man-pages — signal-safety(7)

For a simple single-threaded application, let the handler assign a volatile sig_atomic_t flag. Let ordinary control flow do the complex work. This limited use of volatile is about communication with an asynchronous handler; it is not a general inter-thread synchronization mechanism.

Masks close a timing window

Suppose main code checks child_done == 0, then calls pause. The child terminates and the handler sets the flag after the check but before pause. The signal is already handled, so the subsequent pause can sleep indefinitely waiting for another event.

The repair must coordinate the predicate check with unblocking-and-waiting. A typical pattern blocks the relevant signal, checks state, then uses sigsuspend with an appropriate temporary mask so the transition to waiting is atomic relative to delivery. Upon return, recheck the predicate. Merely moving lines closer together does not remove the race. Linux man-pages — signal(7)

One notification is not one event

Standard signals can coalesce while pending. One SIGCHLD does not necessarily correspond to one child to reap. A reaping loop calls waitpid with WNOHANG until no more exited children are currently available, handling error conditions. The program's state tracks the work; the signal is a notification to inspect that state. Linux man-pages — waitpid(2)

For a more complex design, a self-pipe can translate a handler notification into a descriptor event. Its write endpoint must be nonblocking and the handler must tolerate a full pipe rather than block. Another option on Linux is a descriptor-based signal interface with a carefully managed mask. Each design still needs an explicit ownership and event-loss policy.

Job control adds process groups

A shell groups related processes into a job and coordinates which process group owns the terminal. Ctrl-C is not conceptually a loop that individually calls your handler in every process; terminal-generated signals target the foreground process group under the OS terminal rules. A full job-control shell must coordinate groups, waits, terminal state, and races across creation and exec.

Handler correctness has a context

The simple flag pattern assumes a narrow single-threaded use. In a multithreaded program, signal masks are per-thread and process-directed delivery can select an eligible thread. Inter-thread access to ordinary state still requires the relevant language synchronization. A dedicated thread synchronously waiting for blocked signals can simplify a larger service.

If a handler touches errno, preserve and restore it when the surrounding interrupted code depends on it. Keep handler work small enough to reason about at every possible interruption point, not just when main is idle.

Retrieve before looking

Draw the exact interleaving that loses a notification between a predicate check and pause. Then explain why a loop around that same pair still contains a window.

Worked feedback

Main observes false; a signal arrives; the handler sets true and returns; main calls pause and sleeps. A loop only retries after waking, so it cannot repair sleeping after the already-consumed notification. Blocking the signal during the check and atomically changing the mask while waiting closes the relevant gap. The shared predicate remains the source of truth.
