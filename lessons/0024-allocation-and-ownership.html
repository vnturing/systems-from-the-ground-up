Allocation and ownership

Resize an allocation without losing the only pointer on failure.

Builds on Lesson 23: Faults, copy-on-write, and mmap. Follow the course order on a first pass.

An allocation has a protocol

A successful allocation creates storage a caller can own. Borrowers may use it under bounds and lifetime constraints; an owner eventually releases it exactly once. C does not enforce this protocol automatically, so make it visible in API documentation and error paths.

For an array allocation, validate the element count and multiplication before calling the allocator. Check success before dereferencing. Avoid calling an allocation of zero bytes a portable writable object: establish an explicit empty-state policy. The allocator interface documents the behavior and important edge cases. Linux man-pages — malloc(3)

Resizing changes the object's identity

For a nonzero new byte size:

c
void *candidate = realloc(buffer, new_bytes);
if (candidate == NULL) {
    /* buffer is still owned and must be handled */
} else {
    buffer = candidate;
    /* previous pointers into the old allocation are invalid */
}

Check new_bytes arithmetic first. On success, realloc may move storage, preserving the appropriate prefix. Even an unchanged numerical address does not justify continuing to use old interior pointer values; recompute offsets from the new base under the new object's bounds. New bytes beyond the preserved prefix are not automatically initialized.

The direct assignment buffer = realloc(buffer, new_bytes) loses the only pointer on failure if there is no other owner. That is a real ownership leak, even though no invalid memory access occurs immediately.

Error paths are control-flow ownership

Write a resource table for a function: allocation A, descriptor B, allocation C. After each acquisition, ask which earlier resources remain owned if the next operation fails. A single cleanup section can be clearer than duplicated release logic, provided each resource has a well-defined empty state and ownership transfer is explicit.

Do not free borrowed memory merely because a function no longer needs it. Conversely, returning an owning pointer without documenting the caller's obligation makes leaks likely. Ownership is a part of the interface as much as parameter types.

Growth policy is an algorithmic choice

Growing capacity by one element on every insertion can require quadratic total copying when resizing moves allocations. Geometric growth can give amortized constant insertion cost, but increases slack and still requires overflow checks when computing the next capacity.

Distinguish logical length, allocated capacity, and byte size. For a vector of records, valid initialized elements lie below length; available storage lies below capacity; bytes equal capacity times element size only after checked multiplication. An allocation fitting its capacity does not imply every element has been initialized. ASan can catch some invalid accesses, but it does not generally prove your logical initialization invariant. Clang — AddressSanitizer

Retrieve before looking

A vector has length 9 and capacity 16. After a successful resize to capacity 32, which facts remain true automatically, and which must the program establish? Consider pointers into the buffer, existing elements, and new storage.

Worked feedback

The preserved prefix retains its contents up to the lesser old/new size. Old interior pointers must be replaced with pointers based on the new allocation. Length does not become 32 automatically; the new capacity does not initialize new logical elements. The program must update bookkeeping consistently and preserve a valid ownership path. The language allocation rules are in §7.22.3. WG14 N1570 — public C11 committee draft

Transfer

Write a small vector API contract without implementing it. Specify ownership on success and failure for creation, append, resize, and destruction. Then audit Lab 04's arena reset: which borrowed pointers does one reset invalidate?
