Readiness and backpressure

Bound output queues and resume partial work after readiness events.

Builds on Lesson 34: Parse streams, not writes. Follow the course order on a first pass.

Readiness is an invitation to try

A readiness notification indicates that an operation may make progress under the interface's rules. It does not reserve the descriptor's state or promise an entire application message. Use nonblocking I/O so stale readiness cannot unexpectedly block the event loop.

For a write queue, maintain a buffer and sent offset. Positive writes advance the offset; EAGAIN preserves it and waits for future writable readiness; errors enter a defined connection-close path. Registering perpetual writable interest with no pending data can create a busy loop because sockets are often writable. Linux man-pages — write(2)

Edge and level triggering change the loop

Level-triggered readiness can continue reporting while the condition holds. With edge-triggered epoll, process available I/O until it reports EAGAIN, or use another explicitly correct strategy. Reading one chunk and waiting for a fresh edge can leave unread data with no new edge to wake you. The Linux epoll manual explains these semantics. Linux man-pages — epoll(7)

epoll is Linux-specific; macOS provides different mechanisms such as kqueue, and portable poll has its own interface. The transferable skill is maintaining connection state and progress, not memorizing one event API.

Backpressure protects the whole system

If a client reads slowly, generated responses can accumulate. A service that accepts work faster than it can transmit needs a bounded queue and a policy. At a high-water mark, pause intake or decline work; at a lower threshold, resume. Bound per-connection and global resources so many individually small queues cannot exhaust the process.

Dropping arbitrary bytes corrupts framing. If overload requires rejection, reject at a valid protocol boundary or close the connection under the protocol's error rules. Specify what the client can retry safely.

A connection owns more than a descriptor

Track parser state, pending output, request metadata, deadlines, and closing state. A disconnect can happen in any state. Cleanup must release every owned resource exactly once, and asynchronous callbacks must not retain a dangling reference to an already-reused descriptor number or connection object.

Lab 07 is intentionally a one-client-at-a-time blocking reference. Its extension assignment is to design this state machine, not to assume the reference is a scalable production server. The limits of an example are part of its teaching value.

HTTP adds policy beyond readiness

Persistent HTTP connections, request bodies, response framing, and early close rules require the standard's semantics in addition to transport progress. A generic event loop does not make a protocol implementation correct. Read the framing and connection-management sections of RFC 9112 before attempting that extension. IETF — RFC 9112: HTTP/1.1

A slow client is a useful capacity experiment: make it read in small intervals and observe queued bytes, process memory, and response completion. A correct bound should become visible in the queue metric before the machine is exhausted.

Retrieve before looking

A server can generate 2 MiB/s for a client consuming 0.5 MiB/s. Ignoring other effects, how fast does backlog grow? With a 6 MiB queue limit, how long can this continue from empty before policy must act?

Worked feedback

Growth is 1.5 MiB/s, reaching 6 MiB in four seconds. A queue is temporary storage, not a throughput solution. The service must throttle, reject, reduce output, or disconnect under a defined contract. More buffering only extends the time to saturation.

Transfer

Specify per-connection states and resource bounds for an event-driven extension to Lab 07. Include partial header, partial payload, output pending, EOF, timeout, protocol rejection, and shutdown. Name the invariant that prevents two states from both freeing the connection.
