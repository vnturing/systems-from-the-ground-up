Measure a falsifiable claim

Design a benchmark that can disprove your explanation of a speedup.

Builds on Lesson 16: Dependencies limit throughput. Follow the course order on a first pass.
In this lesson

Begin with a question

“Make it faster” is not an experiment. “Changing traversal order reduces elapsed time by reducing cache misses for this matrix size” is a hypothesis with a mechanism, workload, and observable outcomes. It might be false. That is what makes it useful.

Measure elapsed time with a monotonic clock, repeat measurements, retain raw samples, and report the workload and environment. Keep correctness checks outside the timed region where practical. Prevent the optimizer from eliminating the work by consuming and checking its result; do not blanket the program in volatile and accidentally benchmark a different problem.

Separate useful metrics

Elapsed time includes waiting and scheduling. CPU time counts time charged to execution under the platform's accounting rules. Instructions retired measure one aspect of work; cycles reflect time spent while a counter runs. Instructions per cycle is a ratio, not a universal efficiency grade. A memory-bound program can have low IPC for a real reason.

On Linux, begin with perf stat ./program when permissions and hardware support permit. Add selected counters only when they answer a question. Events and their meanings differ by processor and may be unavailable in a VM. Gregg's examples demonstrate how to collect evidence and note tracing overhead. Brendan Gregg — perf examples

Derive the upper bound

If fraction p of baseline runtime improves by factor s and the rest is unchanged, normalized new time is (1-p) + p/s. Overall speedup is its reciprocal. With p = 0.6 and s = 2, new time is 0.7 and speedup about 1.43. Even an infinitely fast improved component cannot exceed 1/(1-p) under these assumptions.

The assumptions matter: workload is fixed, overhead is accounted for, and the improvement does not change unaffected costs. Real parallelization can introduce synchronization, memory traffic, and a different bottleneck.

Relate work to data movement

Arithmetic intensity is useful operations per byte transferred at a specified memory boundary. If a toy machine sustains 40 GB/s and an algorithm performs two useful operations per eight bytes transferred, its bandwidth bound is 10 billion operations/s at that boundary. Compare with the compute bound and take the lower bound on achievable throughput in this simplified model.

Do not substitute source-level bytes for measured memory traffic without checking reuse and write policies. Different cache levels have different boundaries.

Noise is an investigation input

Warm caches, page faults, CPU frequency, thermal limits, background work, allocator state, and input distributions can change results. Interleave A/B runs or otherwise control drift. Compare distributions, not just one minimum. Establish a stable baseline before interpreting a small difference.

Gregg's USE method prompts resource questions about utilization, saturation, and errors. Apply that as a hypothesis checklist when a benchmark becomes a system investigation. Compiler optimizations can also remove or transform supposedly equal work, so inspect the generated program. Brendan Gregg — the USE method GCC — optimization options

Retrieve before looking

A fivefold improvement affects only 20% of baseline runtime. Calculate the overall speedup. Then name one observation that would refute your claim that the improved region is responsible for a large total gain.

Worked feedback

New time is 0.8 + 0.2/5 = 0.84; speedup is about 1.19. A twofold overall gain cannot follow from those fixed fractions alone. Either your fractions, measurement, workload, or “unaffected” assumption is wrong. A profile showing the region was only a small share of the original run would challenge the attribution.
