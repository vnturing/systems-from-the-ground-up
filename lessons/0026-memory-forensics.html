Memory forensics

Choose evidence that distinguishes leaks, retention, corruption, and virtual reservations.

Similar graphs can have different causes

A process's memory usage rises. Possible explanations include more live application data, lost owning pointers, allocator retention, file-backed residency, copy-on-write, thread stacks, and reserved virtual ranges. “Memory leak” is one hypothesis, not a synonym for every upward line.

Start by specifying the metric: virtual mapped bytes, resident pages, private dirty pages, or requested live allocation bytes. These measure different layers. A Linux memory map shows ranges and permissions; it is not a heap ownership graph. Linux man-pages — proc_pid_maps(5)

Four investigations, four kinds of evidence

For a suspected leak, track allocations and ownership over a repeated steady-state workload. After equivalent work, does unreachable or unreleased allocation state grow? Leak tooling can help where available; platform support differs.

For corruption, find the earliest invalid access with ASan or a watchpoint and a reproducing input. The later allocator abort is a witness. For excessive retention, compare live requested bytes with allocator-held capacity and RSS across repeated cycles. For a huge virtual reservation, observe how many pages are actually accessed/resident rather than assuming the entire mapping is physical memory.

ASan is primarily an access/lifetime instrumentation tool; leak detection may be supplied by related runtime components and is not equally available on every platform. It does not replace a domain-specific ownership argument. Clang — AddressSanitizer

Build a repeatable memory experiment

Choose a workload cycle, such as parse 1000 requests and discard all per-request state. Establish what should survive the cycle: configuration, caches, worker threads. Warm up intentionally, then measure several equivalent cycles. A bounded cache can legitimately grow during warmup and plateau.

Record input sizes, object counts, requested bytes, and process metrics. If requested live bytes return to baseline but RSS does not, investigate retention and fragmentation before declaring a leak. If live bytes rise by one request object per cycle, inspect the release path or a reference that unnecessarily extends lifetime.

Repair the violated contract

A leak repair restores ownership on every relevant path. A corruption repair establishes bounds or lifetime. A retention repair may require different pooling or object lifetimes rather than more calls to free. A capacity problem may require a bound or backpressure. These remedies address different mechanisms.

A stable average can still hide a failure

A mean request size can look harmless while rare large requests retain oversized buffers per worker. With 100 workers each keeping one 16 MiB buffer, retained capacity reaches roughly 1.6 GiB before other state. An experiment must reflect tail sizes, concurrency, and reuse policy.

The allocator's documented behavior explains why release and OS reclamation do not have a one-to-one relationship. Gregg's resource-oriented method helps frame memory saturation and error questions without beginning from one favorite metric. Linux man-pages — malloc(3) Brendan Gregg — the USE method

Retrieve before looking

After each workload cycle, requested live bytes return to 2 MiB, mapped virtual bytes remain at 1 GiB, and RSS stabilizes at 50 MiB. What can you conclude, and what cannot you conclude?

Worked feedback

The observed requested-live metric and RSS plateau do not show unbounded growth in those measurements. They are compatible with reservation and retention. They do not prove every object is correctly owned, that all paths are safe, or that a different input distribution cannot cause growth. You need definitions and coverage for the metrics before calling the program leak-free.
