Storage is not a promise of a live object

A pointer bug is often a time bug. This function has an invalid result contract:

c
int *bad_result(void) {
    int local[2] = {6, 9};
    return local; /* local stops existing at return */
}

The pointer may retain a familiar-looking address, but its target's lifetime has ended. A test that “still prints 6” does not rescue the program. Rewrite the interface so the caller provides storage, or allocate storage with explicit ownership and a matching release. The relevant lifetime and storage-duration rules are in §6.2.4. WG14 N1570 — public C11 committee draft

Automatic storage typically serves ordinary local variables; static storage serves objects that persist for the program's duration; allocated storage persists until released. These language concepts are more reliable than saying “all locals live on the stack”: an optimizer can keep a value in a register or remove it entirely.

Layout adds invisible bytes

Consider a record used for a file format:

c
#include <stddef.h>
struct Record { char kind; int value; char active; };

On a common implementation where int has size and alignment four, kind starts at offset 0, value at 4, and active at 8. Tail padding can make the total size 12. Use sizeof(struct Record), _Alignof(struct Record), and offsetof(struct Record, value) to inspect your own implementation.

Why the gaps? An object's alignment constrains acceptable addresses. Padding helps successive members and successive array elements meet those constraints. Field order can change the size. Do not turn the example's measured offsets into a promise about every compiler, ABI, or packed layout.

Writing the struct's raw bytes to a socket is consequently a poor portable wire format. It leaks padding and ties interpretation to field sizes, byte order, and layout. Later we will serialize fields explicitly.

Ownership makes allocation usable

A minimal allocation pattern is:

c
#include <stdlib.h>
int *make_value(int n) {
    int *p = malloc(sizeof *p);
    if (p != NULL) *p = n;
    return p; /* caller owns success and must free it */
}

malloc supplies suitably aligned storage for ordinary object types and can fail. sizeof *p measures the pointed-to type without evaluating a load. A caller checks for NULL, uses the live object, and calls free exactly once. Dereferencing afterward is invalid even if the allocation system has not reused the bytes. Linux man-pages — malloc(3)

Undefined is not random

Undefined behavior means the language imposes no requirements for that execution. It is not a specified lottery among a few amusing outcomes. Optimizers reason under the assumption that valid executions respect language rules; a lifetime or alignment mistake can therefore change behavior far from the bad line.

Keep three categories distinct: defined behavior you can rely on, implementation-defined behavior the implementation documents, and undefined behavior you must prevent. Instrumentation such as UBSan checks selected violations, not every condition required for a valid program. Clang — UndefinedBehaviorSanitizer

Retrieve before looking

A caller allocates a record, stores its address in two pointers, frees one, and reads through the other. Does having a second pointer keep the object alive? Explain without referring to whether the program crashed.

Worked feedback

No. Both values designated the same allocation; neither was a reference count. free ended that allocation's usable lifetime. The second pointer is now dangling. A crash is only one possible symptom. Repair the ownership protocol: exactly one owner releases storage after all permitted borrowers finish.

The first source is the recommended primary reading. Read for the question taught here; these links are extensions, not prerequisites to understanding the page.

    Language contracts: §§6.2 (types, lifetime, representation), 6.3 (conversion), 6.5 (expressions), 7.22.3 (allocation), 7.17 (atomics). The labs compile as C17 and use the shared subset; this older draft is not the final C17 standard.

    Allocation, overflow risks, failure handling, and realloc ownership.

    Instrument selected undefined operations. Use diagnostics as evidence, not a complete proof of correctness.
