Coherence and false sharing

Distinguish correct sharing from unnecessary cache-line contention.

Builds on Lesson 19: Locality and blocking. Follow the course order on a first pass.

The hardware tracks lines, not intentions

Two cores can cache copies of the same memory region. A coherence mechanism coordinates access so the architecture's rules for a location are respected. A core that writes may need exclusive ownership of a line, invalidating or changing another core's copy. This traffic can become expensive when ownership moves repeatedly.

If each thread updates a different counter but both counters occupy one coherence line, their logical independence does not prevent hardware contention. This is false sharing. If they update the same counter, the sharing is real; padding cannot remove the logical coordination requirement.

First establish a valid program

Do not benchmark plain unsynchronized increments to shared C objects and describe any odd output as “the cache did not flush.” A C data race is a language-level correctness failure. Use synchronization or distinct independently accessed objects with valid lifetime and publication. Later lessons establish those contracts.

For a simple false-sharing experiment, use one relaxed atomic counter per thread, then compare tightly adjacent counters with deliberately separated ones. Check alignment and the target's relevant line size. Keep the total work and memory ordering constant between variants. Atomic counters make the increments well-defined; they do not make the contention disappear.

Design an alternative explanation

Suppose separation improves elapsed time. Competing explanations include changed alignment, different compiler code, scheduling, migration, and a larger working set. Inspect addresses and instructions. Repeated runs and appropriate hardware events can strengthen the coherence explanation, but event names and availability vary.

A stronger design often accumulates into thread-local values and combines once. This reduces the frequency of shared writes instead of merely separating them. The reduction itself needs a sound ownership/synchronization protocol. Measure total runtime, including the final combination.

Coherence is not a whole-program order

Coherence concerns coordination of accesses to a location or line under an architecture. It does not by itself promise that independent writes become visible in the source order needed for a multi-object publication protocol. Compiler reordering and CPU memory ordering add separate constraints. User-space C atomics express those constraints at the language level; hardware manuals describe how targets implement them. Intel — architecture and optimization manuals

Keep memory models in their own domain

The Linux kernel memory-barrier guide provides detailed examples of ordering and compiler effects. It explicitly describes kernel mechanisms and caveats; copying a kernel barrier into a C user program is not a substitute for the C memory model. Linux kernel — memory barriers

Drepper's paper offers useful historical coherence experiments and layout reasoning. Modern cores, interconnects, and NUMA systems vary. In NUMA, placement adds another dimension: local and remote physical memory can have different costs, even when cache layout and synchronization are correct. Pinning and placement can help experiments but also change the workload you are measuring. Ulrich Drepper — What Every Programmer Should Know About Memory

Retrieve before looking

Why might one atomic increment per item scale worse than one atomic addition per completed batch? Does relaxing memory order remove the requirement to coordinate writes to the same counter?

Worked feedback

Batching reduces the number of shared ownership and atomic-update operations. Relaxed ordering can remove some ordering constraints, but each update to the same atomic object still participates in its atomic modification order and must coordinate correctly. It is not an instruction to allow lost updates. If a batch's result must be visible with other data, specify the publication protocol too.

Go to the source

The first source is the recommended primary reading. Read for the question taught here; these links are extensions, not prerequisites to understanding the page.

  • Ulrich Drepper — What Every Programmer Should Know About Memory

    Practitioner investigation of memory hierarchy, locality, and coherence. Published 2007: do not treat its hardware sizes or timing as current constants.

  • Intel — architecture and optimization manuals

    Instruction semantics, architectural state, exceptions, and memory-management rules. Timing varies by microarchitecture.

  • Linux kernel — memory barriers

    Advanced comparison for compiler/CPU ordering. Kernel primitives and the Linux memory model do not replace C's user-space atomics contract.
