Lab 08 · 4–6 hours, with extensions

A queue that drains and stops

Predict. Run. Explain. Preserve the evidence.

Download all lab files ↓ Environment setup

The question

Can producers and consumers process each work item exactly once, stay bounded, and shut down without stranded waiters? The reference has one producer, several consumers, a bounded ring, predicate-based waits, and graceful close/drain semantics.

sh
python3 labs/check.py --lab 8
cc -std=c17 -Wall -Wextra -Wpedantic -pthread labs/08-queue/queue.c -o queue
./queue 4

The checker uses capacity one and eight with one, two, and seven consumers, repeating each case. It checks completed item count, exact sum, and a per-item seen array after all threads have joined. A matching sum alone would not exclude every duplicate/missing pair.

Annotate the contract

Write which mutex protects queue slots, head, tail, count, and closed. The result counters have a separate mutex, and final inspection occurs after join. Explain why moving the final read into the producer loop without synchronization would change the correctness argument.

Trace full-queue and empty-queue waits. Both conditions are checked in loops under the queue mutex. A return from pthread_cond_wait includes reacquisition; it does not reserve an item. Close broadcasts to all relevant waiters, prevents further insertion, and allows existing items to drain.

Extend the failure matrix

  1. Add a controllable item count so you can test zero items and fewer items than consumers. Keep the backing seen-array capacity and actual produced range distinct.
  2. Close before any submission, then verify producers receive the documented failure and consumers terminate.
  3. In a scratch variant, replace a wait loop with if; use a schedule argument to demonstrate the defect even if a stress run happens not to expose it.
  4. Add heap-owned work items on paper and define who releases them after completion, failed submission, or cancellation.

Observe with instrumentation

On a supported platform, build a separate -fsanitize=thread executable with debug symbols. Do not combine it with ASan. Record whether the runtime is available and whether tested executions report races; do not claim silence proves the whole design.

Completion criteria

Submit invariant comments, shutdown order, adversarial cases, unique-item checks, and a wait graph for one intentionally broken design. Report throughput separately from correctness. If worker count changes performance, identify a competing explanation rather than assuming “more threads should be faster.”

Investigation guidance

The shutdown sequence is: set closed and broadcast while holding the mutex, unlock, join users, then destroy synchronization objects. Joining while holding the mutex can prevent consumers from reacquiring it to observe close. A condition variable is not a stored item count; the protected queue state is the source of truth.

Depth extension

Compare a per-item shared statistic with thread-local accumulation and one final reduction. Then compare adjacent versus separated atomic counters while preserving synchronization semantics. Distinguish true sharing, false sharing, and result-publication requirements before interpreting a speed difference.
