Lab 09 · 6–10 hours, with extensions

A source-to-hardware investigation

Predict. Run. Explain. Preserve the evidence.

Download all lab files ↓ Environment setup

The assignment

Evolve the bounded frame service into a small system you can explain at every boundary. Choose either a correctness investigation or a measured performance improvement, and defend the result with reproducible evidence. The provided reference implementations and check harness are your baseline, not a finished concurrent server.

Required baseline

Run all native lab checks and preserve the output. Run sanitizer checks where supported. Add the real TCP-loopback path where permitted. Document unexecuted platform-specific steps. Keep byte-for-byte transformation correctness for empty, maximum, binary, fragmented, combined, oversized, and truncated cases.

Choose a focused project

  1. Correctness: implement an incremental frame decoder and prove invariance to all single split points plus random partitions. Add zero-length and truncated-input checks.
  2. Concurrency: connect the frame service to a bounded worker queue. Specify admission, per-request ownership, response ordering, and close/drain behavior. Include a client that disconnects during processing.
  3. Performance: identify a repeatable hot path, change data layout or buffer reuse, and compare useful throughput and response latency with the same correctness oracle. Keep tail-size and slow-reader cases.

Complete one project deeply before combining them. A design that changes parser, queue, allocator, and transport at once makes causal claims harder to defend.

The investigation report

Use labs/09-capstone/report-template.md. Include the contract ledger, baseline, hypothesis, competing explanation, minimal intervention, exact reproduction commands, raw samples, and practical limits. Include one annotated artifact below source level: assembly, relocation, mapping, descriptor trace, or measured counter evidence.

Assessment rubric

Score each item 0 (missing), 1 (plausible but incomplete), or 2 (demonstrated with inspectable evidence):

CriterionWhat earns two points
RepresentationExplicit width, byte order, length bound, and boundary cases
MemoryOwnership, lifetime, overflow checks, and exercised error paths
ControlDescriptor/process/thread lifetimes, cleanup, and shutdown
CorrectnessExact oracle and adversarial cases, including truncation
MechanismLayer-specific causal explanation and competing hypothesis
MeasurementReproducible commands, raw data, and honest uncertainty
TransferOne new input or machine condition predicted before running

A strong submission has no zero in correctness, memory, or control and can explain every assumption behind its evidence. The score is a review aid, not an externally accredited qualification. There is no automated script claiming to grade the complete capstone.

Review prompts

Ask whether a plausible response arrived for the right request, whether a rejected frame allocated resources first, whether every closed connection frees exactly one owned state object, and whether the measured speedup preserved the useful-work contract. Demand an explanation for any missing check. A limitation stated precisely is stronger than a broad unsupported claim.

After the course

Bring a minimal reproducer or focused artifact question to a relevant technical community. Offer the hypothesis and evidence, not a wall of logs. Then return to the teaching workspace with your result so the agent can record demonstrated understanding and choose the next challenge.
