Lab 06 · 2–4 hours, with extensions

Copy every byte, report every failure

Predict. Run. Explain. Preserve the evidence.

Download all lab files ↓ Environment setup

The question

Does your byte-transfer loop preserve progress under partial success and interruption? The reference copies arbitrary binary input from standard input to standard output. Its success contract is delivery through the output descriptor, not crash-durable storage.

sh
python3 labs/check.py --lab 6
cc -std=c17 -Wall -Wextra -Wpedantic labs/06-io/copy.c labs/06-io/io.c -o byte-copy
printf 'a short example\n' | ./byte-copy

Inspect the real injected boundary

io-test.c compiles the actual write_all implementation with its write dependency replaced by an injected function. It does not reimplement the helper. The injected writer verifies each requested offset/length and produces counts 3, -1/EINTR, 2, and 5. Separate scenarios return zero progress and EPIPE.

Write the expected invariant before reading the assertions: [0,done) has been transferred exactly once and [done,length) remains. Explain why a negative result is checked before conversion to size_t. A zero-progress response for a nonempty request must not produce an infinite loop.

Run system-level checks

The checker copies empty input, one null byte, and a repeated binary sequence larger than the buffer. It compares exact output bytes. It also directs output into a pipe with no reader and checks that the utility reports failure rather than silently succeeding. SIGPIPE is deliberately ignored so the ordinary error path can observe EPIPE.

These tests address different boundaries: injected partial transfers check algorithmic progress; binary copying checks actual I/O; the closed reader checks failure reporting. None establishes persistent storage semantics.

Change the contract deliberately

Design a read_exact result type distinguishing complete data, clean EOF before any new record, truncated record, and system error. Then compare with the helper used by Lab 07. A single Boolean “read succeeded” loses information the protocol needs.

As an extension, design a nonblocking version whose state persists across calls. It must return “wait for readiness” rather than retry EAGAIN in a busy loop. Specify who owns the unsent buffer between events.

Completion criteria

Submit a progress table, actual failure output, binary-equivalence evidence, and two explicitly different success contracts: ephemeral transfer and durable file replacement. Identify the extra synchronization/namespace questions in the durable case; do not label fflush a universal power-loss guarantee.

Investigation guidance

After three bytes, retry at offset three with seven remaining. EINTR in the injected sequence makes no progress. After the next two, resume at five with five remaining. Resending the full input duplicates bytes. Adding the signed error return to an unsigned cursor corrupts bounds. The correct no-progress/error path terminates with an error, preserving the caller's ability to decide what happens next.

Depth extension

Add a fault-injected reader and test EOF at every possible record boundary. For each failure, explain what data was already delivered and whether a retry of the whole operation could duplicate externally visible work.
