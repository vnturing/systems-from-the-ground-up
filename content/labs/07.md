## The question
Can a service preserve framing under arbitrary stream chunking and reject oversized/truncated input? The reference transforms ASCII `a`–`z` into uppercase, leaving other byte values unchanged. Each request and response has a four-byte big-endian length followed by that many payload bytes. Maximum payload: 4096. Empty frames are valid.

```sh
python3 labs/check.py --lab 7
```

The default checker passes connected Unix-domain sockets to the actual compiled handler. It tests ordinary, empty, maximum, binary, combined, individually split, oversized, and truncated frames without needing permission to bind a TCP port. These sockets exercise stream semantics and the real parser/helper, not the TCP listener setup.

Where local network binding is allowed, also run:

```sh
python3 labs/check.py --lab 7 --loopback
```

This adds the real IPv4 loopback listener/client path. The environment in which this course was authored restricted binding; keep this distinction visible rather than claiming an unexecuted listener check passed.

## Run the listener manually
Compile `server.c` together with `labs/06-io/io.c`. Invoke it with a positive connection count, such as `./server 3`. It prints `PORT=...`, binds only to `127.0.0.1`, and serves that many connections sequentially. Use a separate client terminal to connect to the announced port. This small reference has no production deadline or concurrency implementation; a client that stops mid-frame can block it.

## Account for state and ownership
1. Trace a header split after its second byte. Show which call resumes and where the next bytes go.
2. Trace two frames combined in one send. Show why the second frame is not lost.
3. Trace zero length. No payload read should be required, and a response still contains a zero-length header.
4. Trace EOF during a header and during a body. Neither is a successful frame.
5. Trace 4097 as a declared length. It must be rejected before payload allocation or an unbounded wait.

TCP send boundaries may be coalesced; splitting writes does not force the receiver's exact read chunk sizes. The invariant must hold for every permitted split, not just one observed schedule.

## Deliverables
Supply a protocol specification, state diagram, rejection table, evidence from compiled checks, and a descriptor/resource lifetime diagram. Explain why this is not an HTTP server and why send success is not proof of remote business-operation completion.

::: solution Investigation guidance
The header decodes with explicit unsigned shifts, independent of host byte order. `read_exact` preserves partial progress; the caller interprets EOF in context. A bounded stack buffer prevents advertised lengths from turning into unbounded allocation, but the length check still must precede its use. The reference's sequential scheduling is a capacity limitation, not a framing defect.
:::

## Depth extension
Design an incremental nonblocking parser with per-connection output offsets, high/low water marks, total request deadlines, and bounded global resources. Keep the reference tests and add a slow-reader workload. If you choose HTTP instead, implement its actual framing standard rather than rebranding this protocol.
