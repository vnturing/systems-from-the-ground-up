## The question
Does traversal order change useful work per transferred cache line for your workload? The reference traverses the same matrix in row and column order, verifies matching sums, and consumes the result so the work has an observable purpose.

```sh
python3 labs/check.py --lab 3
cc -std=c17 -O2 -g labs/03-locality/matrix.c -o matrix
./matrix 1024
```

## Predict before measuring
For the selected dimension, calculate element size, row stride, total footprint, and useful elements per assumed line. Use the cache workbench to construct a conflict trace separately; the browser model is not your CPU.

Predict which dimension ranges might fit in a cache and where the traversal difference could become visible. Your prediction may be wrong because of compiler transformation, prefetching, associativity, or a mistaken model. That is a result to investigate.

## Collect interpretable samples
1. Run sizes 17, 257, 1024, and a larger size within the documented maximum 4096 if your memory budget permits. The largest matrix is about 64 MiB on the intended target.
2. Record repeated runs with OS, architecture, compiler, flags, and background load. The reference always times rows first, which biases warm-cache conditions. Create a variant alternating order and justify its warmup policy.
3. Inspect optimized assembly or compiler reports for loop transformations. If the compiler removes the intended contrast, describe that observation and construct a controlled alternative; do not silently claim the source order is the executed order.
4. On a suitable Linux environment, add `perf stat` events that address your hypothesis. If counters are unavailable, report the limitation and use timings plus artifact evidence without inventing miss counts.

## Implement and justify one extension
Add blocked traversal with clipped edge tiles. Preserve the exact integer sum for non-multiple sizes. Compare several tile sizes rather than presenting one lucky parameter as universal. Alternatively investigate independent unsigned accumulators while keeping traversal fixed; treat that as a distinct experiment.

## Completion criteria
Provide raw samples, the correctness oracle, calculated footprint/stride, generated-code evidence, and a conclusion limited to the tested workloads. No automated test asserts that one order must be faster; performance is an observed property under stated conditions.

::: solution Investigation guidance
A large row-major matrix makes row traversal contiguous and column traversal stride by a full row. That mechanism predicts useful-byte differences, but small footprints and compiler transformations can erase the measured contrast. A valid negative result identifies why your model might not distinguish the tested cases. For blocking, use `min(start+tile,n)` carefully and test edge rows/columns.
:::

## Depth extension
Produce a roofline-style model at a named memory boundary and an Amdahl bound for optimizing the measured region inside a larger request path. Explain which byte-traffic estimate is measured and which is assumed. A single elapsed-time ratio cannot establish a complete microarchitectural story.
