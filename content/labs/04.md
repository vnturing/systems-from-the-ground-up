## The question
Can a tiny allocation interface make bounds, alignment, failure, and lifetime obvious? The reference arena owns a 128-byte aligned backing array and uses a cursor. It supplies byte storage, not a general drop-in allocator for arbitrary typed objects.

```sh
python3 labs/check.py --lab 4
python3 labs/check.py --lab 4 --sanitize
```

## Inspect before changing
Trace the provided requests by hand. Identify why alignment validates powers of two and limits requests to the backing buffer's alignment. Show that subtraction-based capacity checks prevent cursor arithmetic overflow. A failed call must leave the cursor unchanged.

The backing array has a declared character-array type. For the provided exercise use returned ranges as byte buffers and copy representations with `memcpy`. A general allocator intended to host arbitrary C objects needs appropriate backing-storage and effective-type reasoning; a cast alone does not establish it. This limitation is deliberate and prevents a small example from making a broader promise than its representation supports.

## Extend the meaningful checks
1. Test every supported power-of-two alignment with multiple preceding cursor positions. Verify returned address alignment and non-overlap of live byte ranges.
2. Test exact fit, one byte too large, zero size under this API's explicit rejection policy, invalid alignment, and `SIZE_MAX` requests.
3. Reset, then reuse the entire capacity. Explain why old pointers are invalid under the arena API even though their numerical addresses can reappear.
4. Add an optional allocation-mark/rewind operation. Specify whether rewinding invalidates all later objects and what prevents an invalid mark from moving the cursor out of bounds.

## A deeper design exercise
Sketch a free-list allocator with block headers, minimum block size, aligned payloads, splitting, and coalescing. Draw a trace that creates external fragmentation and another that creates internal slack. Then define a structural checker before implementing any extension: region partition, valid block sizes, free-list uniqueness, and no overlap.

The reference arena and its tests are complete. The free-list design is an extension project with no hidden completed implementation. A correct allocator extension should be judged by its invariants and adversarial traces rather than a few successful allocations.

## Completion criteria
Submit annotated capacity arithmetic, new boundary checks, ownership/lifetime documentation, and a fragmentation diagram. Distinguish requested live bytes, arena capacity, mapped virtual memory, and resident physical memory. Explain why `arena_reset` is not an OS request to unmap memory.

::: solution Investigation guidance
With cursor 13, alignment eight, and size sixteen, padding is three and the new cursor is 32. Failure must preserve the old state. Checking `size > remaining-padding` after validating padding avoids computing an overflowing speculative end. Reset changes the arena's logical lifetime state; it does not erase the bytes or guarantee RSS decreases.
:::

## Depth extension
Use the arena for request-scoped byte parsing, then introduce one long-lived retained object. Measure how lifetime grouping can retain more memory than live payload size suggests. Propose an interface that prevents accidental escape of a short-lived borrowed buffer.
