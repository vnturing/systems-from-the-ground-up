## Build a machine small enough to reason about
An instruction-set architecture specifies observable machine behavior. A microarchitecture implements it. Two processors can execute the same instruction set with different pipelines, caches, execution widths, and timings. Never turn a simple teaching pipeline into a literal schematic of every modern CPU. Intel's manuals separate architectural behavior from processor-specific optimization guidance. [[intel]]

For a first timing model, give each instruction five stages: fetch, decode, execute, memory, and writeback. Assume one cycle per stage and one new instruction entering per cycle. Without overlap, eight instructions take 40 stage-cycles of elapsed time. With ideal overlap, the first finishes at cycle five and the eighth at cycle twelve.

Latency is the time for one instruction to pass through. Throughput is the completion rate once overlap is established. Pipelining improves the latter without necessarily reducing the former. Clock frequency alone does not tell you either program runtime or useful work per second.

## Derive where the model fails
A data hazard occurs when an instruction needs a result not yet available. Forwarding may supply it before writeback, but a load's value still depends on memory. A structural hazard occurs when two operations need a resource the model cannot serve simultaneously. A control hazard occurs when the next instruction address depends on an unresolved branch.

Take `load a; add a, b; store b`. The add depends on the load, and the store depends on the add. If the memory access takes longer, simply drawing more overlap does not create the missing value. Add a stall or a different execution mechanism to your model, then recompute the timeline.

## Combinational work and saved state
A datapath contains computations such as adders and selectors, plus state such as registers. Combinational logic maps current inputs to outputs; state elements preserve values across clock boundaries. A clock period must accommodate relevant propagation and state-transition requirements. Splitting work into more stages can shorten some paths but adds pipeline overhead and complicates hazards.

This explains why “double the stages” is not a universal “double the performance” rule. Branch recovery, forwarding, power, and implementation complexity interact. Programmer-visible instruction count is also not necessarily the internal operation count.

::: deep Modern execution preserves a simpler appearance
An out-of-order processor may issue ready operations before older stalled operations, rename registers to remove false dependencies, and predict branches. It still needs to preserve architectural rules for completed execution, including exceptions. Speculative work can be discarded architecturally while affecting caches and other microarchitectural state.

You do not need a transistor-level model to debug a dependency-bound loop. You do need to identify the assumptions behind your timing claim. “One cycle per source line” and “all independent operations are free” are both unsupported models. Compiler transformations further change the relationship between source and instructions. [[opt]]
:::

## Retrieve before looking
For an ideal six-stage pipeline and ten instructions, derive elapsed cycles, steady-state throughput, and the latency of one instruction. Then say which result changes if every instruction depends on an unavailable previous result.

::: solution Worked feedback
Elapsed time is `6 + 10 - 1 = 15` cycles, throughput after filling is one instruction per cycle, and single-instruction latency is six cycles. Dependencies can force stalls and reduce realized throughput, invalidating the fifteen-cycle prediction. The baseline six-stage latency remains the model's latency absent those extra stalls.
:::
