## Addresses expose structure
For a genuine contiguous C array `int a[rows][7]`, each row contains seven integers. On our four-byte-int target, `a[i][j]` has byte offset `(i*7 + j)*4`. The row stride is 28 bytes; the column stride is four.

A compiler might compute `i*7` as a shift and subtraction, or combine address calculations in another way. An instruction's scale factor need not spell the source dimension directly. Reduce the arithmetic first, then propose a data layout.

A pointer-to-pointer representation is different: `int **p` commonly requires loading a row pointer before locating an element. Those rows need not be adjacent. A contiguous 2D array does not decay into `int **`; the row type matters. The array and pointer rules in the language draft explain the distinction. [[c]]

## Field offsets constrain hypotheses
Suppose a function loads one byte from offset 0 and a four-byte value from offset 8 of the same base pointer. That is evidence for two fields or accesses at those offsets. It does not uniquely reveal member names, padding, or the full record size.

Write a candidate struct and inspect it with `offsetof` and `sizeof`. If your candidate places the second field at offset 4, it does not explain the observed offset 8 without an additional assumption. Debug information can reveal declared types when available, but stripped machine code often leaves several candidates.

A structure's alignment and aggregate passing rules also affect function boundaries. Small structs may travel through registers; larger ones may use memory or hidden pointers. Use the target ABI rather than the assumption “a struct argument is always copied on the stack.” [[abi]]

## Turn reverse engineering into a falsifiable claim
Start with a statement such as “this address equals base plus 28*i plus 4*j.” Then list candidate interpretations: a seven-column integer array, a byte buffer with equivalent strides, or part of a larger packed layout. Choose an input that distinguishes them when you control execution. A hypothesis that explains one input but not the stride over many rows is incomplete.

Object-file metadata can help: symbol size, alignment, and section placement constrain possibilities. `readelf` exposes ELF metadata, but does not reconstruct absent source names by magic. [[readelf]]

::: deep Padding changes arrays of records
If a record's fields occupy 13 bytes but its alignment is eight, its size may round to 16. Then adjacent records start 16 bytes apart. A load with stride 16 may reflect tail padding, not a hidden four-byte field. Reorder fields experimentally, recompile, and compare both `sizeof` and generated addressing.

For a portable wire format, avoid guessing a native struct declaration that happens to match one capture. Decode explicit byte fields. Matching one ABI's padding is not a protocol specification.
:::

## Retrieve before looking
An access uses `base + i*40 + j*8`. Under the hypothesis of a contiguous matrix of eight-byte elements, how many columns are there? What other evidence would you seek before asserting that hypothesis as fact?

::: solution Worked feedback
Five columns: the row stride is 40 bytes and each element occupies eight. Seek loop bounds, allocation size, adjacent access patterns, debug types, and caller contracts. Those may support or disprove the matrix interpretation. The address arithmetic alone also fits other layouts.
:::
