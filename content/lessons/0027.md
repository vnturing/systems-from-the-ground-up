## Control flow is larger than function calls
A normal call transfers between instructions in a process under an ABI. A system call deliberately requests an operating-system service through a privileged entry mechanism. A fault or other synchronous exception is associated with the current instruction. An external interrupt arrives independently of that user's current source line.

The precise categories and names vary by architecture. On x86, consult the architecture manuals for interrupt, fault, and trap semantics instead of mapping every event onto a C function call. The OS saves and restores required execution state, chooses a handler, and decides whether and where execution continues. [[intel]]

## User code requests a service
Calling the C library's `read` interface may eventually enter the kernel to obtain bytes from a descriptor. The library function's calling convention and the kernel's system-call ABI are separate interfaces. A compiler-generated ordinary function call is not automatically a privilege transition.

The kernel validates arguments and permissions. For a pointer to a user buffer, a plausible numerical address is not enough. The requested range must be usable under the operation's rules. A successful system call may still transfer fewer bytes than requested. A failed call is reported through its interface's return/error contract. [[read]]

## A process can stop being the running process
During kernel work, a scheduler may run something else, especially if the caller waits for I/O. A context switch saves enough state to resume one execution context and restores another. This is distinct from a mode transition: the kernel can handle a short service and return to the same process without scheduling a different one.

Likewise, a library call may be satisfied mostly in user space and perform no system call on that invocation. Do not infer privilege transitions merely from source-level function names.

## Signals are an OS-to-process interface
A signal is not the CPU exception handler itself. The OS may deliver a signal in response to a fault, a terminal action, another process, or a timer. Delivery can run a user-space handler under constraints or take a default action. Blocking, pending state, and disposition are separate parts of the model. [[signal]]

::: deep Restarting an instruction is a contract
A recoverable page fault can establish a mapping and resume the faulting instruction. Other synchronous events may resume after an instruction or terminate execution. Precise exceptions require the visible architectural state to correspond to a meaningful point even when the microarchitecture did speculative work.

For debugging, ask: which operation caused the transition, what state was saved, which handler/interface runs, and what continuation is permitted? That question set connects a syscall trace, a debugger backtrace, and a fault report without pretending they are the same view.
:::

## Retrieve before looking
A program waits in `read`, another process runs, a device completes work, and the original program later resumes. Identify a syscall boundary, a scheduling event, and a possible interrupt without collapsing them into one event.

::: solution Worked feedback
The user enters the kernel to request `read`. If bytes are unavailable, the task may block and the scheduler can run another task. Device completion may generate an interrupt that lets the kernel make progress and wake the waiter. The waiter runs when scheduled, and the syscall eventually returns under its byte-count/error contract. Exact paths depend on the descriptor and implementation.
:::
