## Names are not connections
A hostname and service identify a lookup request, not a ready socket. `getaddrinfo` returns candidate addresses with family and socket information. Iterate candidates deliberately: create a matching socket, attempt the operation, close failed candidates, and release the result list. Use its error-reporting interface rather than assuming every lookup failure is an ordinary `errno` failure. [[dns]]

An endpoint includes an address and a port under a transport protocol. A connection uses local and remote endpoints plus protocol/state. DNS, routing, transport establishment, and application behavior can fail independently. “The network is broken” does not identify a layer.

## Listen and accept create different responsibilities
A server creates a socket, binds an address, and listens. `accept` returns a connected socket; the listening socket remains responsible for new connections. Closing one does not automatically close the other. Each accepted descriptor needs its own ownership and termination path.

Lab 07 binds only to IPv4 loopback and lets the OS choose an available port. This is a deliberately small local experiment, not an Internet service. Its address choice keeps setup focused; the general lesson still includes address-family-independent resolution and candidate iteration.

## TCP does not deliver messages
TCP provides an ordered reliable byte stream while the connection is functioning under its protocol rules. Reliability does not mean an application can never see failure, nor does it create record boundaries. A read can return less than one message, several messages' bytes, EOF, or an error. RFC 9293 is the primary protocol specification. [[rfc9293]]

A successful local send does not prove the remote application processed or durably stored the bytes. Application acknowledgments and idempotency rules solve higher-layer questions. Retrying after a disconnected connection can duplicate an operation if the server completed it before the acknowledgment was lost.

## Separate clocks and limits
Connection establishment, idle time, total request time, and processing deadlines are distinct policies. A peer that sends one byte occasionally can defeat a timeout that resets indefinitely on every byte. Bound frame length and overall work even in a teaching service.

On Linux, socket options, buffering, and transport behavior have detailed contracts in `tcp(7)`. Avoid changing options based on folklore before identifying the workload and latency/throughput objective. [[tcp]]

::: deep Backlog is not application capacity
A listening backlog concerns queued connection states under OS rules; it is not the worker queue or a guarantee of useful throughput. Accepted connections can each retain buffers and descriptors while waiting. Capacity must include those resources and the application's admission policy.

A remote close can produce EOF in one direction while the other direction still has meaning. TCP supports half-close; protocols must define whether and when a client signals end-of-request by length, delimiter, or closing a direction. Our framed protocol uses explicit lengths, preserving the ability to exchange several frames on one connection.
:::

## Retrieve before looking
A hostname resolves, but connect fails; another connection succeeds but the application waits forever for a newline that was never sent. Which layers succeeded, and where would you investigate each failure?

::: solution Worked feedback
Resolution succeeded in the first case; connection establishment did not, so inspect candidate address, endpoint, routing, listener, and reported error. In the second, transport establishment succeeded; the application framing contract is mismatched. Neither symptom is repaired by assuming DNS was wrong. Collect evidence at the failed boundary.
:::
