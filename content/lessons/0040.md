## Choose one system and follow its boundaries
The capstone is a bounded loopback frame service evolved from Labs 04, 06, 07, and 08. It receives a four-byte length header, validates a bounded body, performs a deterministic transformation, and returns a framed result. You will add an investigation harness and one justified improvement rather than build a giant application.

Start with the blocking reference. Establish correct behavior for ordinary, empty, maximum-length, fragmented, oversized, and truncated input. The reference intentionally has limited concurrency; replacing it with a worker pool is an extension that requires explicit queue and shutdown contracts. Do not call the service HTTP: RFC 9112 specifies a different protocol. [[http]]

## Build a contract ledger
At the representation boundary, specify header width, unsigned range, and byte order. At the C boundary, specify buffer capacity, initialized length, and ownership. At the process boundary, specify descriptor ownership and exit status. At the concurrency boundary, specify queue invariants and publication. At the performance boundary, specify useful work and workload distribution.

A broken system often has individually plausible components with incompatible contracts. The ledger makes those mismatches inspectable before they produce a mysterious symptom.

## Make a claim that can lose
Choose one target: a parser that mishandles fragmented input, an unbounded queue, a memory lifetime error, a traversal hotspot, or a lock-held I/O path. Write symptom, competing hypotheses, predicted observations, and an intervention.

Examples of useful evidence include a failing protocol test, sanitizer report, annotated assembly, descriptor table, queue-depth series, or repeated timing samples. Select evidence for the question rather than collecting every metric available. Gregg's resource-oriented method and profiling examples provide practitioner models for this discipline. [[use]] [[perf]]

## Separate a repair from an improvement
A repair restores the intended contract. An optimization preserves the contract while improving a measured property for a defined workload. You may do both, but report them separately. Keep the baseline and changed implementation, the same oracle, and raw samples.

After a memory repair, rerun the original reproducer and relevant boundary inputs with supported instrumentation. ASan provides concrete evidence for exercised accesses, not a blanket proof of lifetime correctness. Explain the invariant that now prevents the invalid operation. [[asan]]

::: deep Write for a skeptical future reader
Your report should let someone reproduce the result without this conversation. Include OS and architecture, tool versions, build flags, exact commands, workload generation, expected outputs, raw observations, and limitations. Link observations to claims: “RSS plateaued under this workload” is stronger and narrower than “there are no memory problems.”

For performance, include correctness and tail behavior. A service with excellent average throughput but unbounded slow-client buffering can still fail its mission. For concurrency, include close/drain behavior and prove no waiter is stranded. For protocols, include adversarial chunk boundaries rather than only polite clients.
:::

## Retrieve before looking
A profile shows most sampled CPU time in parsing, but wall time is dominated by waiting for a slow reader. Which metric should guide a latency fix? What would you measure next?

::: solution Worked feedback
Wall-clock response time is the target if the mission is latency. An on-CPU profile describes where execution time goes while running; it does not account for all waiting. Measure pending output, peer consumption, blocking/readiness state, and end-to-end timing. Then test a backpressure/deadline policy. Making parsing faster may barely change the user's wait.
:::

Complete Lab 09's rubric and close the source-to-hardware loop. Explain one request as encoded bytes, C operations, compiled instructions, memory accesses, kernel I/O, and synchronized ownership. You are ready to extend the course when you can defend that account and identify what remains uncertain—not when every page has a checkmark.
