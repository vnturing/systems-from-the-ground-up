## A fault can be useful work
A user load or store can trigger a synchronous exception when translation or permission checks need help. The operating system examines the address, mapping, and access. It may establish backing storage and resume the instruction, or reject the access and report a fault to the process.

Demand allocation lets a process reserve a virtual range without immediately populating every page with private physical storage. Consequently a successful allocation call does not prove every byte is resident or that future physical-memory pressure cannot cause problems. Observe the distinction between virtual size, resident memory, and application-requested bytes.

## Copy-on-write preserves separate semantics
After `fork`, parent and child have separate address spaces with initially corresponding contents. An implementation can share physical pages read-only until a write requires a private version. The performance trick must preserve the process contract: one process's ordinary private write is not a write to the other's independent object. [[fork]]

This explains why a tiny child that immediately executes another program need not copy every byte of a large parent's memory eagerly. It also explains why a child that dirties many pages can incur substantial memory work. “Fork is free” and “fork always copies the entire heap immediately” are both inadequate models.

## Map a file deliberately
For file-backed `mmap`, choose shared versus private behavior, access permissions, length, and offset. Check for `MAP_FAILED`. Offsets have page-alignment constraints; map a suitably aligned range and account for an internal displacement when the logical record starts later. Keep the file's length and lifetime assumptions explicit. [[mmap]]

A mapped load can fault when the page is first accessed. Access beyond valid backing-file conditions can fail in ways different from a checked `read` returning an error code. Another process truncating a mapped file changes the experiment's assumptions. The apparent convenience of array indexing does not remove I/O failure modes.

## Inspect without overclaiming
On Linux, compare the process map before and after a mapping or allocation. Then distinguish that map from residency/accounting observations. `/proc/PID/maps` describes ranges and permissions; it cannot alone answer how much private physical memory the process currently consumes. [[maps]]

::: deep Minor, major, and fatal are different axes
Linux fault accounting distinguishes faults that require I/O from those that do not under its documented accounting behavior. A recoverable copy-on-write or demand-zero event can be a minor fault. A major fault generally involves I/O work. An invalid access can instead lead to a signal such as `SIGSEGV`; a backing-file problem can produce `SIGBUS` on relevant mappings.

Avoid diagnosing every segmentation fault as “out of RAM” or every major fault as “swap.” File-backed demand paging is another source of I/O. Connect the fault to the mapping and workload before choosing a remedy.
:::

## Retrieve before looking
A process maps a 1 GiB file privately, reads one byte, then writes one byte. Does that imply one GiB of private resident memory? Which events might differ between the read and the write?

::: solution Worked feedback
No. Mapping establishes a range; access determines which pages need backing and become resident. The read may establish or reuse a file-backed page. A private write may require copy-on-write storage for that page. Actual accounting depends on OS state, page size, readahead, and existing cache. Estimate at page granularity rather than equating mapped length with private RSS.
:::
