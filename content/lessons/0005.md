## A bit pattern needs an interpretation
Eight bits `11110010` can mean the unsigned integer 242, a signed two's-complement value of -14, or part of an instruction. Storage alone does not carry your intended interpretation. With unsigned width `w`, bit `i` contributes `bit[i] × 2^i`; summing those contributions gives a value from 0 through `2^w - 1`.

Hexadecimal compresses four bits per digit. `0xB6` is `1011 0110`: `11 × 16 + 6 = 182`. Group binary from the least significant end when converting. Hex is not a different kind of memory; it is a way to write a value.

The browser workbench below uses eight-bit bytes and finite widths. These are explicit model assumptions; the C language defines a byte through `CHAR_BIT`, which is at least eight. Our Linux/macOS lab targets use eight.

## Byte order answers a different question
For the value `0x0A1B2C3D`, a little-endian four-byte encoding places `3D 2C 1B 0A` at increasing addresses. A big-endian encoding places `0A 1B 2C 3D`. Neither description reverses the order of bits within each byte. x86's architectural documentation specifies little-endian integer storage. [[intel]]

To decode little-endian bytes `b0`, `b1`, `b2`, `b3`, compute `b0 + 256*b1 + 65536*b2 + 16777216*b3`, using a sufficiently wide unsigned type. To encode, repeatedly extract the low eight bits and shift right. This explicit conversion works independently of the host's native byte order.

## Masks are small set operations
For an unsigned value `x`, `x & 0x0F` retains the low four bits. `x | mask` sets selected bits; `x & ~mask` clears them; `x ^ mask` toggles them. `x >> k` moves bits toward the low end. Shift counts must stay within the promoted operand's width, and signed shifts require additional care. The integer promotions occur before these operations. [[c]]

A packed header could place a three-bit type above a five-bit length. For byte `0xB6`, type is `0xB6 >> 5 = 5`; length is `0xB6 & 31 = 22`. Notice that this is about fields in one value, not about multi-byte endianness.

::: deep Read representations without inventing objects
You can inspect an object's bytes through `unsigned char *`, and use `memcpy` to copy a representation into suitable storage. Casting an arbitrary address to `uint32_t *` can add alignment and effective-type problems even on a CPU that tolerates some unaligned loads. Conversely, a C access can be invalid before the hardware raises any exception. The language model and hardware model must both be satisfied.

For an on-disk format, state field width, signedness, byte order, and bounds separately. “It is a 32-bit number” leaves too many unanswered questions.
:::

## Retrieve before looking
Decode `81 02` as little-endian unsigned 16-bit. Then take the low five bits of `0xB6`. Work in hex first and decimal second.

::: solution Worked feedback
`0x0281 = 2 × 256 + 129 = 641`. The low-five-bit mask is `0x1F`; `0xB6 & 0x1F = 0x16 = 22`. If you obtained `0x8102`, you assigned the first byte the high significance. If you obtained six for the mask, you kept four bits instead of five.
:::
