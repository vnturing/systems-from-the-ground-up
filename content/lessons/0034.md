## A parser is a state machine
Define an original binary protocol: a four-byte unsigned big-endian length followed by exactly that many payload bytes. Permit lengths from zero through 4096. The length excludes the header. This simple format is intentionally not HTTP.

A streaming decoder has header state and payload state. Header state accumulates four bytes. Once complete, decode the length and reject values above the limit before allocating or waiting for that payload. Payload state collects or processes exactly the declared number of bytes. Completing a frame returns to header state, possibly consuming another frame from the same input chunk.

TCP's byte-stream contract requires this independence from read boundaries. [[rfc9293]]

## Work a split input
The bytes `00 00 00 03 63 61 74` encode payload `cat`. Suppose input arrives as `00 00`, then `00 03 63`, then `61 74`. After chunk one, header state holds two bytes. After chunk two, the header is complete and payload state holds `c` with two bytes remaining. Chunk three finishes the frame.

Now concatenate a second complete frame to the final chunk. A correct decoder continues parsing; it does not discard bytes after the first completed payload. EOF with no partial header is a clean end between frames; EOF after two header bytes or in a payload is truncation. The underlying `read` interface supplies counts and EOF, not the protocol classification. [[read]]

## Length checks come before resource commitments
A malicious or buggy peer can advertise billions of bytes. A bound protects memory and work, but the parser must also check arithmetic such as header length plus payload length when storing combined frames. Set a limit justified by the service, not by the largest representable integer.

Zero-length frames are valid in this lab's protocol. They finish immediately after the header, so the state machine must make progress without waiting for a nonexistent payload. Explicitly test this case; otherwise a loop can stall with zero bytes remaining.

## Feedback requires adversarial chunking
Lab 07's reference server uses an exact-length blocking helper for one bounded frame at a time. The browser workbench uses incremental parsing to expose arbitrary chunks. Both must produce the same frame sequence for every splitting of the same complete stream. Test all single split points and randomized multi-chunk partitions.

::: deep Protocol ambiguity is a security issue
HTTP/1.1 has more complicated framing rules, including interactions between length fields and transfer encodings. RFC 9112 defines parsing and message-length rules precisely. When two intermediaries disagree about boundaries, one stream can be interpreted as different request sequences. [[http]]

Our lab removes those complexities to teach a crisp invariant: consumed bytes belong to exactly one header or payload, length is bounded before commitment, and leftover bytes are preserved. Generalizing to HTTP requires implementing the actual standard, not renaming this toy decoder.
:::

## Retrieve before looking
Decode `00 00 00 00 00 00 00 02 4F 4B`. How many frames are present and what are their payload lengths? What changes if EOF arrives before the final byte?

::: solution Worked feedback
There are two frames: an empty payload and a two-byte payload `OK`. If the final byte is absent at EOF, the second frame is truncated; the first remains a completed frame. Do not confuse a zero length with EOF, and do not treat the remaining partial payload as a successful message.
:::
