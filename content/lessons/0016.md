## Count chains, not just instructions
Consider a sum `s += a[i]`. Every update reads the preceding value of `s`. If an addition has latency three cycles on a chosen machine, that chain cannot start dependent additions every cycle merely because several add units exist. This is a latency-bound recurrence.

Unrolling four iterations into four consecutive updates to the same `s` reduces loop overhead but retains the chain. Using four independent accumulators creates four shorter chains and combines them at the end. The change can expose instruction-level parallelism; its benefit depends on loads, execution resources, register pressure, and the final reduction.

## Distinguish true and false dependencies
A read-after-write dependency carries a value required by the computation. Register renaming cannot remove it. Reusing an architectural register name for unrelated values can create write-after-write or write-after-read naming conflicts; a renaming implementation may eliminate those conflicts internally.

Compilers also face aliasing uncertainty. If a store through one pointer may change a value read through another, moving the read across the store may change valid program behavior. `restrict` can give a useful non-aliasing contract, but violating that promise makes the source invalid. It is an obligation on callers, not a magic speed annotation.

## SIMD needs compatible work
A vector instruction can operate on several lanes. This is different from overlapping independent scalar instructions, although both can coexist. A loop with independent elementwise operations is a better candidate than a loop where each element depends on the previous result.

Compile a simple array transformation with GCC's vectorization reports (`-fopt-info-vec-optimized` and `-fopt-info-vec-missed` on supported GCC versions). For Clang, use its corresponding optimization remarks rather than passing GCC-only options blindly. Look at assembly and measured behavior, not just whether a report says “vectorized.” [[opt]]

## Preserve the algorithm's numerical contract
For unsigned modular addition, reassociating a sum preserves the modular result. For floating-point addition, changing grouping can change the rounded answer. A multi-accumulator sum may therefore be a different numerical algorithm. Choose a correctness tolerance based on the task before judging the speedup. Goldberg's analysis explains why real-number algebra is insufficient. [[float]]

::: deep Bounds for a first performance model
Suppose a toy machine can execute two additions per cycle, but each addition's result takes three cycles. One independent recurrence achieves at best one addition every three cycles. Three independent recurrences can in principle hide the latency up to one addition per cycle; six may be needed to reach two per cycle, ignoring all other resources.

These are model bounds, not promises for your CPU. Loads may dominate; instruction decoding may constrain issue; more accumulators may spill registers. Use model predictions to choose measurements. Processor optimization manuals supply target-specific constraints, while your compiled binary supplies the actual instruction stream. [[intel]]
:::

## Retrieve before looking
Does replacing one accumulator with four guarantee a fourfold improvement? Name two conditions that can prevent it and one condition under which the transformation can alter the result.

::: solution Worked feedback
Memory bandwidth, issue limits, register spills, and loop overhead can all constrain the gain. Floating-point reassociation can change results. If your explanation is only “the CPU is faster,” identify a resource or dependency and predict a measurable consequence, such as fewer cycles with similar bytes transferred.
:::
