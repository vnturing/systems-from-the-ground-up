## Addresses are interpreted in a context
A pointer's numerical address in a user process is normally a virtual address. Translation maps a virtual page to a physical frame under that process's address-space context and checks permitted access. Two processes can use the same virtual number for unrelated physical storage; they can also deliberately map the same physical storage at different virtual numbers.

Assume a toy 16-bit virtual address and 256-byte pages. The low eight bits are the offset; the high eight bits are the virtual page number, or VPN. Virtual address `0x1234` has VPN `0x12` and offset `0x34`. If VPN `0x12` maps to physical frame `0x2A`, the physical address is `0x2A34`. This is our original example of the paging mechanism described in OSTEP. [[paging]]

## Translation and permission are separate outcomes
A page-table entry can encode a frame and flags such as presence and allowed access, depending on architecture. A read-only mapping cannot satisfy a user write merely because a frame exists. An absent translation may lead to an operating-system fault handler; it is not automatically a disk read or a fatal crash.

The browser translator uses a small explicit mapping table with present and readable flags. It is a teaching model. Real x86-64 and AArch64 page tables have architecture-specific formats, multiple levels, and more permission/context details. Do not treat the toy table as a register layout.

## Map regions, not individual variables
Operating systems manage mappings at page granularity. A small out-of-bounds C access can remain inside a valid writable page, so it may not trigger a hardware protection fault. Conversely, a valid request for an as-yet-unbacked mapped page can fault and recover normally. This is why page protection and C object safety solve different problems.

On Linux, inspect `/proc/PID/maps` for a known process. It shows virtual ranges and permissions, not the address of each C object or a complete residency report. Dynamic allocation may obtain memory through different underlying mechanisms; “the heap” is a useful label, not a guarantee that every allocation comes from one contiguous range. [[maps]]

::: deep Shared mappings and aliases
A file can be mapped into multiple processes. A shared mapping and a private copy-on-write mapping differ in what writes mean. `mmap` specifies mapping flags and error behavior; callers must test for `MAP_FAILED`, which is not the same failure sentinel as `malloc`'s `NULL`. [[mmap]]

An address-to-frame diagram should label the address space, page size, VPN, frame, offset, and permissions. Without the address-space label, a shared numerical address may be mistaken for shared storage. Without the permission check, translation may look like unconditional arithmetic.
:::

## Retrieve before looking
With 1024-byte pages, split virtual address `0x2ABC`. If its VPN maps to frame 7, calculate the physical address. Then say what additional condition must hold for a user write to succeed.

::: solution Worked feedback
Ten low bits form the offset: `0x2ABC = 10*1024 + 700`, so VPN is 10 and offset is 700 (`0x2BC`). Physical address is `7*1024 + 700 = 7868`, or `0x1EBC`. The mapping and access mode must permit the write, and other architecture-specific checks must succeed. A correct sum does not bypass protection.
:::
